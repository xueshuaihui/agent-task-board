
# HTML Page Generator

创建可直接运行的单文件 HTML，默认适配手机和桌面浏览器。

本 Skill 含两条**相互独立**的 track，共用同一个技能入口。每轮第一步先做线路分流，分流后两条 track 的规则互不适用。

- **应用 track（「工作流」节）**：把自然语言需求转化为可直接体验的单文件 HTML 应用；固定流程为输入准入 → 整理 Spec → 按需信息收集 → 创建页面 → 自查与验证 → 多轮修改。交付形态只有单文件前端 HTML。
- **文档渲染 track（「文档渲染 track」节）**：只做**一篇已有内容的格式转换**——把文稿确定性渲染为带预置视觉主题的 HTML，内容与章节结构不变，agent 只选主题、不设计版面，也不自行搜集内容。产物为静态文档，该 track **不做应用交付能力评估**。命中条件、内容源形态与负样本以「线路分流」判定链为唯一口径。

## 线路分流（MANDATORY，先于一切能力评估与全局规则）

每轮**第一步**只做分流，不做交付能力评估、不读 `references/intake.md`、不写任何文件；允许用 `Glob` / `Read` 只读探查内容源，仅为判定内容门槛，不产生任何写入。

**总判据：本轮产物是「一篇文稿的排版」，还是「一个页面的设计与行为」。**

- **文档渲染 track**：一篇文稿的网页版——报告、文档、说明、总结、清单式资料，从上到下读完；交互只作阅读辅助（目录跳转、锚点、折叠、打印、深浅色），图表静态呈现即成立。命中即**静默转入「文档渲染 track」节**，不播报路由，**不经过「工作流」的输入准入及任何步骤**。
- **应用 track**：产物响应用户输入并改变状态——筛选、排序、搜索、表单、计算、编辑、增删、登录、多页导航、游戏、动画、可交互看板与地图；**或产物虽零交互、但价值在于现场设计的版面本身**（见「形态门槛的定义域」）。进入「工作流」第 1 步。

**唯一判定链（依序短路，任一步判入应用 track 即停止）：内容门槛 → 形态门槛（定义域）→ 信号与删交互。** 走文档渲染 track 必须依次通过前两关；只有信号都不明显时才进第三关。三处只在此定义，下文与 `references/*.md` 只引用不复述。

- **内容门槛（第一关）**：可排版的内容**当前已存在**，落在三种来源之一——已有 md 文件、随 query 附的正文、本轮上文已形成且可逐字或成段取回的内容（三种子模式见 `references/doc-render.md`）。**磁盘有无 Markdown 不是判据**，但内容必须已存在且可取回；本 track **不自行搜集内容**。只给主题、内容尚不存在需现场搜集，或上文已被压缩到只剩摘要无法取回原材料时，本关**不成立**：即使形态像报告，也静默转应用 track（「工作流」第 1 步）由其搜集并产出。
- **形态门槛（第二关）**：本轮产物是一篇连续文稿的排版（见「形态门槛的定义域」），不是版面设计或交互行为。不成立即转应用 track，**哪怕零交互**。

| | 文档渲染 track | 应用 track |
|---|---|---|
| 产物本质 | 一篇文稿的排版 | 一个页面的设计与行为 |
| 版式从哪来 | 预置主题，agent 只选不设计 | 现场设计 |
| 内容与产物的关系 | 一对一映射，结构不变 | 可重组、重编排 |
| 分叉层 | 只在 CSS / 样式层 | HTML 结构与行为层 |

### 形态门槛的定义域（判定链第二关，先于信号裁决）

先过内容门槛（第一关）再进本关。文档渲染 track 只做**一篇文稿的格式转换**：载体从 Markdown / 对话正文变成 HTML，内容与章节结构不变，视觉来自预置主题。命中必须**同时**满足：

1. **文稿性**：内容是连续文稿——成段落的正文、表格、清单，有（或能自然形成）章节层级，可一对一映射为 Markdown 的 `##` 章节。
2. **版式无需设计**：产物 = 这篇文稿 + 一套预置视觉主题。版式由渲染脚本确定性产出，agent 只**选主题**，不设计版面。

任一不满足即走应用 track，**哪怕产物零交互**。以下都是零交互却归应用 track 的典型：

| 需求类型 | 为何不是格式转换 |
|---|---|
| 落地页 / 活动页 / 营销单页 | 需现场设计首屏、视觉动线与 CTA 编排 |
| 产品展示页 / 品牌介绍页 | 版面即产物价值，不是文稿的排版 |
| 个人主页 / 在线简历 | 版式高度定制，预置主题不适用 |
| 海报 / 邀请函 / 单页视觉物 | 无章节文稿结构 |
| slide / 演示页 | 分页视觉单元，不是连续文稿 |
| 以图文视觉编排为主的介绍页 | 内容被重新编排，非一对一映射 |
| 用户指定了具体版面（首屏这样做、这里分两列、用某品牌色） | 超出「选主题」范围 |

**「零交互」不等于「文档渲染 track」。** 定义域不成立即进应用 track，**不做删交互测试**；定义域成立但出现强应用交互信号（如给了 md 却要加筛选 / 排序 / 编辑）时也直接判应用 track，交互才是本体。仅当定义域成立、且信号都不明显时，才进「歧义裁决」的删交互测试。

### 形态信号

| 类别 | 信号 |
|---|---|
| 读物（强） | 转换 / 转成 HTML / 转成网页 / 排版 / 网页版 / 出一份报告 / 导出；「美化」指向已有文稿时 |
| 应用—有交互（强） | 筛选 / 排序 / 搜索 / 切换 / 输入 / 计算 / 编辑 / 增删 / 登录 / 游戏 / 可交互看板 / 动画 |

零交互的应用信号不在此列，全部由定义域表承担。信号只用于判定链的形态归属，不改写内容门槛的结论：内容已存在于三种来源之一时，**不因磁盘没有 Markdown、或内容只在本轮上文而改判应用 track**——缺的只是一步固化，不是形态变化；内容不存在需现场搜集时内容门槛已在第一关否决，不再进入信号裁决。

### 歧义裁决（删交互测试，判定链第三关）

仅在内容门槛与定义域均成立、且信号都不明显时进入本关（强信号已在前两节直接定性）。做删交互测试：把产物里所有交互功能删掉，剩下的还是不是一件完整的交付物？

- 是 → 文档渲染 track（交互只是增强）
- 否 → 应用 track（交互是本体）

测试仍判不出时（例：「把这些数据做成一个页面」），由**文档渲染 track 发起一次形态确认询问**（选项用用户可理解的产品语言描述：一份可直接阅读、可打印的报告页面 / 一个可以筛选和交互操作的页面）；用户选择交互形态后才转入应用 track。**未确认前不得默认落应用 track。**

### 对照样本

| 需求 | track | 理由 |
|---|---|---|
| 上文刚收集完信息，用户说「帮我转换为 html」 | 文档渲染 | 强读物信号，内容已在上文锚定 |
| 「把这份报告转成网页，带目录导航」 | 文档渲染 | 目录是阅读辅助 |
| 「出一份 X 行业报告网页」（零内容，需现场搜集） | 应用 | 内容门槛不成立：本 track 不自搜集，转应用 track 搜集并产出 |
| 上文已搜集好资料，用户说「整理成一份 X 报告网页」 | 文档渲染 | 内容已存在于上文（内容门槛成立），只做排版 |
| 「搜集 X 资料并做成可交互看板」 | 应用 | 内容需搜集 + 产物是交互看板，两道门槛都指向应用 |
| 会话中已有应用项目目录，用户新给内容要求排版 | 文档渲染 | 自建独立输出目录，不触碰应用项目目录 |

**同一需求不得同时启动两条 track。**

### 分流的边界（MANDATORY）

- 分流只判断「走哪条 track」，**不判断「该不该做」**。「工作流」第 1 步的输入准入、`NEEDS_USER_DECISION` 与 `STOP_UNSUPPORTED` 均为**应用 track 专属**，一律不适用于文档渲染 track。
- 宿主层选中本技能后，分流只能在这两条 track 之间选择，**无法退回宿主重选其他技能**。「整理信息 + 做成网页」这类链式需求按内容门槛裁决：**内容已存在于本轮上文**时在文档渲染 track 内闭环（该 track 只固化已有内容再渲染，不新增搜集）；**内容尚不存在、需要现场搜集**时归应用 track，由其在「工作流」第 3 步搜集后产出。
- 输入是 `.docx` / `.pdf` / 图片等非 Markdown 载体、意图仍是文稿排版时，只要能取回可用的 Markdown 或纯文本即视为内容门槛成立，**留在文档渲染 track**；确实取不到时如实说明缺什么并停止，**不得静默转为应用 track 现场重画排版**。
- 反向同理：定义域不成立时，**不得因为「看起来是读物」或「反正没交互」而留在文档渲染 track**，拿预置主题代替用户要的版面设计。
- 本阶段除「歧义裁决」的形态确认外不消耗「需求处理」的询问预算，不额外增加询问轮数。

## 工作流（应用 track）

本节及以下「交付底线」「需求处理」「语言一致性」只在分流落到**应用 track** 后生效，对文档渲染 track 一律不适用（见「文档渲染 track」节）。输入准入是应用 track 专属阶段，文档渲染 track 不经过输入准入。

1. **输入准入**：读取 `references/intake.md`，在零文件写入状态判断本轮需求是否适合单文件前端 HTML。命中 `STOP_UNSUPPORTED` 或安全红线时说明替代形态后停止；命中 `NEEDS_USER_DECISION` 时按其「询问方式」集中询问一次并等待答复；`DIRECT` 时静默继续。
2. **整理 Spec**：读取 `references/simple-spec.md`，在内部整理当前版本 Spec（含 REQ 编号与验收标准）；不向用户展示 Spec，也不将 Spec 写入任何文件。
3. **按需信息收集**：读取 `references/research.md`，判断是否需要补充真实世界信息。不需要则直接进入下一步；需要则用 `ra_search` 工具搜集并在内部整理 Research Notes，搜索失败不阻塞流程。
4. **创建页面**：读取 `references/quick-html.md` 创建页面；涉及图片时按 `references/images.md` 处理图片链路（image-search skill检索、本地/用户图上传换 URL）。
5. **自查与验证**：按 `references/self-review.md` 与 `references/quick-html.md` 的「检查与验证」完成一轮有界自查（`scripts/check-page.mjs` 是可选的静态检查工具，判断有机械出错风险时直接调用，不要反复重读产物）；自查只决定交付说明里写什么，不决定要不要交付，随后一律按交付协议输出结果。
6. 用户对已交付页面提出修改或补充时，必须先重新读取 `references/quick-html.md` 再动手，按其「多轮修改」规则判断采用增量修改还是重新生成，产出新版本文件并重新完成验证与交付；每一轮修改都必须以交付协议收尾。

## 交付底线（应用 track）

- 凡本轮创建或修改了页面文件，回复必须包含独立的 `MEDIA:/root/userdata/workspace/html-gen/<项目目录>/<文件名>` 行：顶格书写，不在代码块或列表中，必须是含项目目录一层的绝对路径；仅口头说明“已完成”视为交付失败。**输出这一行的唯一前提是文件已真实写入磁盘**；自查结论、残留问题、未清零的检查项均不构成不输出的理由。
- 同一项目的首版与后续所有迭代版本均写入同一个项目目录，目录名为 `<基础名>-<YYYYMMDD-HHMMSS>`（首轮用 `date +%Y%m%d-%H%M%S` 一次性确定，后续轮次不重取），不同项目各自成目录；目录命名、目录定位与版本规则以 `references/quick-html.md`「输出文件」为准。
- 自查未通过、检查项未清零或存在已知残留问题时，**照常输出 `MEDIA:` 行**，同时用用户语言如实说明哪项未通过和建议的下一步，不得宣称“检查通过”；只有本轮根本没有产物文件（未写盘、写盘失败或文件为空）时才没有 `MEDIA:` 行，此时必须说明原因，不静默结束。

## 需求处理（应用 track）

- 先读取用户提供的文档、数据、图片和其他素材，再整理 Spec。
- 素材读取失败时（文件不存在、路径不可访问、格式无法解析）如实说明该素材未采纳，改用示例数据或降级方案继续，不静默忽略，也不把未读到的内容当作真实信息写进页面；图片素材读取失败按 `references/images.md` 的「降级顺序」承接槽位。
- 内容依赖实时或外部事实时，先用 `ra_search` 获取并核对；无法获取时明确使用示例数据，不得编造为真实信息。
- 需求足够明确时直接执行；仅在缺少无法合理推断的关键信息时集中询问一次（与准入阶段共享同一次询问预算）。
- 用户要求“直接做”或“你决定”时采用合理默认值，不增加确认环节。
- 对真实后端、数据库、登录鉴权、真实 API、多端原生应用或生产级工程需求，能否直做/先问/停止以 `references/intake.md` 为准；可交付时说明本 Skill 只交付单文件前端体验，可用 Mock 数据或浏览器本地状态演示，但不得声称已真实接入。

## 语言一致性（应用 track）

- 本节只约束生成过程中的沟通语言，不约束交付物：页面内的标题、界面文案等语言完全由需求内容决定。
- 「用户语言」指用户本轮输入所用的语言，即当前正在处理的这条用户消息：用户中途切换语言时，后续过程性输出跟随切换。
- 用户消息混杂多种语言时按此判定用户语言：用户显式指定沟通语言时以指定为准；否则先剥离术语性英文（技术名词、产品名、API 名等），以叙述主体语言（动词、连接词等句法骨架所用语言）为准，不按字符占比统计；仍无法判定时沿用会话已建立的语言。
- 所有过程性输出——集中询问、能力边界与限制说明、进度同步、交付说明——必须使用用户语言，单轮回复内和多轮迭代间均不得漂移或混杂其他语言。
- Spec 整理使用用户语言，包括在思考过程中整理时；技术名词、API 名等术语可保留英文原文。
- 思考过程中的执行叙述（需求复述、开工播报、文件命名、检查验证等决策说明）同样使用用户语言。
- 代码与注释、搜索 query 按执行效果自主选择语言，不受本节约束；`MEDIA:` 行是协议格式，保持原样输出。
- 思考过程内容不得直接搬入回复正文；无论思考使用何种语言，底线保证是：每一条对用户的回复都必须与用户语言保持一致。

## 文档渲染 track（MANDATORY）

分流命中文档渲染 track 时，静默读取 `references/doc-render.md` 并完全按其执行，不进入「工作流」的任何步骤。

- **不经过输入准入**：「工作流」第 1 步的交付能力评估、`NEEDS_USER_DECISION`、`STOP_UNSUPPORTED` 对本 track 一律不适用。
- **跳出本 track 的两个出口**：内容根本不存在、需要现场搜集时，属内容门槛不成立，静默转应用 track（「工作流」第 1 步）；预置主题盖不住实际的版面需求时，说明后回「线路分流」重新分流，**不拿主题套一个交差的结果交付**。内容源子模式、事实约束分级、交付说明分级及内容源指认询问，均以 `references/doc-render.md` 为准。
- 不创建应用项目目录、不复用会话中已有的应用项目目录；输出目录由该文件自建。
- 不做 `-vN` 版本定版、不写 MANIFEST、不走应用 track 的交付脚本。
- 不读 `references/intake.md`、`references/simple-spec.md`、`references/research.md`、`references/quick-html.md`、`references/images.md`、`references/self-review.md`，也不跑 `scripts/check-page.mjs`。
- **不适用应用 track 的全局规则**：「交付底线」「需求处理」「语言一致性」均只服务应用 track，对本 track 一律不适用；本 track 所需的运行环境约定与交付规范由 `references/doc-render.md` 自带一份，不从本文继承。
- 本文对本 track 只提供技能入口与「线路分流」。除上述边界外，本文不对其执行、沟通与交付施加任何约束，全部细则以 `references/doc-render.md` 为准。
