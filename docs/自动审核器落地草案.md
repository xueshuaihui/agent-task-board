# 自动审核器落地草案 · 修订版「审核即任务」（2026-09-29 讨论稿）

> 状态：**待用户审核**。本版是对上一版的推翻重写。
> 触发原因：上一版把「审核」做成平台侧的第二套认领体系（`claim_next_review` / `submit_review`），
> 违背了本产品的基本分工——**平台客户端只负责任务下发与异步技能承载，不直接提供 agent 操作**。
> 审核既然是一种工作，就该以任务形态下发，走所有工作共用的那条认领链路。

## 1. 原则重申（本版的设计公理）

| 原则 | 含义 | 上一版的违背点 |
|---|---|---|
| P1 平台是看板，不是执行者 | 平台只做三件事：存数据、下发任务、回写状态。任何「模型判断」都不发生在平台进程里 | 无违背（这条本来就守住了） |
| P2 **一切工作皆任务** | Agent 能做的每件事都以任务出现，经 `claim_next_task` 认领、以租约持有、用 `complete_task` 回写 | `claim_next_review` 给「审核」开了一条**不走任务认领、不带租约**的专用队列，等于在任务体系外挂第二类工作 |
| P3 技能随任务下发 | 判据/方法以技能形式绑在任务上，认领时随载荷送达（0919 10.3 已验收） | rubric 曾考虑「服务端常量写死」，绕过了技能面 |
| P4 Agent 凭证面只有一条通路 | Agent 只能经 MCP 或 `/api/v1/tasks/*` 的 Agent 路由进来；用户接口一律 UI-only（15 章铁律，有鉴权隔离用例锁死） | 无违背 |
| P5 平台不起进程、不设计时器 | Q2（09-28）与 Q3（09-28）两条裁定 | 无违背 |

**本版结论**：审核 = 一支「审核任务」。平台在 `complete` 那一刻**派生**它，Agent 用**现有的**认领链路领它、
用**现有的**回写通道把结论**回落**到被审任务。平台全程不做判断、不开新队列、不起进程。

## 3. 方案骨架（审核即任务）

1. **派生（`complete` 那一刻，与三分流同事务）**
   `review_mode=auto` 的任务完成回写时，除现状的 `REVIEW / track=auto` 之外，同事务内建一支审核任务：

   | 字段 | 取值 | 为什么 |
   |---|---|---|
   | `type` | `审核` | 词表见第 5 点，是本方案唯一的词表变更 |
   | `status` | `READY` | 立刻进认领池，走现有 `claim_next_task`；不需要任何新通道 |
   | `title` | `审核 T-1008〈原标题〉` | 短号可跳转，人在看板上认得出这是给 agent 的活 |
   | `priority` | 继承被审任务 | 别让「审」排到被审对象后面 |
   | `parent_task_id` | **留空** | 填了会让被审任务命中「父任务不进 Agent 池」那条过滤，还会被算进需求完成度；关联走 `review_of_task_id` |
   | `review_of_task_id` / `review_of_run_id` | 被审任务与 `current_run_id` | 新列（迁移 0021），是「审谁」的唯一权威，也是自审门禁与回落目标的依据 |
   | `review_mode` | `none` | **审核任务自己不进审核**，否则无限递归；`none` 在这里的含义是「它的 complete 就是结论落地」，不是「免审」 |
   | `skills` | 绑「自动审核判据」技能 | 判据随载荷下发（P3），认领方 `get_task`/claim 就能拿到正文 |
   | `description` | 内联证据 | 见第 2 点 |
   | `origin_type` | `user`（**不动 0013 的 CHECK**） | 语义是「人建单时选了 auto = 委托平台代建一支审核任务」；派生事实由被审任务上的一条 system 评论 + 审计动作 `review_task_spawned` 记录，不新增第三种来源值 |

2. **证据随任务下发，而不是给 agent 开读产物的口子**
   审核任务的 `description` 由平台按固定模板拼装：被审 Run 的 `summary` / `output`、执行日志尾段（现有 `runLogs` 首页量级）、
   产物清单（`type` + 名称 + **`uri` 相对数据目录** + 体积 + `missing`），并对 `text/markdown/json/log/link` 且体积 ≤ 阈值
   （新设置键 `review_evidence_inline_kb`，默认 64）的产物**内联正文**；diff 走 UI 预览那套截断策略，不新造。
   文件与图片只给 uri——审核器与平台同机（本地应用的定义），它有权限读那个路径，比在鉴权面上开口便宜得多。
   **不改 `ArtifactsController` 任何一条 scope**（15 章铁律零风险）。

3. **自审门禁从「提交时」挪到「认领时」**
   `CANDIDATE_SELECT` 加一条 `NOT EXISTS`：审核任务所审 Run（`review_of_run_id`）的执行者 Token == 调用方 Token 时，
   该候选直接跳过。人话：**自己干的活不会派到自己面前**，与 0020 的 `SELF_REVIEW_FORBIDDEN` 同一条硬线，只是换了拦的位置。
   提交侧的硬闸**保留**（防「人手工把审核任务派给执行者」这类绕过）。

4. **结论回落（复用现有回写通道，不开新工具）**
   `completeSchema` 加一块可选字段 `review_verdict`：

   ```
   review_verdict?: {
     conclusion: 'APPROVE' | 'REJECT' | 'ESCALATE',
     suggestion / reason / detail,   // 与 reviewSchema 同一份校验，REJECT 三字段必填
     return_to?: 'READY' | 'BACKLOG',
   }
   ```

   - 校验：`review_of_task_id` 非空的任务**必须**带 `review_verdict`（不带就 422，错误体照 `parseToolInput` 的回显口径给可接受值）；
     普通任务带了也 422（防把结论注到不相干任务上）。
   - 落点：`WritebackService.complete` 识别到审核任务，就在同一笔事务里对被审任务调 `TasksService.submitReview`
     （APPROVE/REJECT）或 `escalateToHuman`（ESCALATE）——**结论落地仍是那一条人审同源的实现，零复制**。
   - 审核任务自己的流转：`RUNNING → DONE`（`review_mode=none`，不经 REVIEW），它的产物（审核报告）挂在它自己的 Run 上，
     被审任务的「审核」Tab 与通知照常显示署名 `Agent · <Token 名>`。
   - 拿不准就 `ESCALATE`：**平台侧的默认保守口径**——`review_verdict` 缺失或 conclusion 越界一律 422，
     绝不代拟 APPROVE。

5. **词表与迁移**
   - 新列（迁移 0021）：`tasks.review_of_task_id` / `tasks.review_of_run_id`（可空 + 索引）。
   - 任务类型：`DEFAULT_TASK_TYPES` 追加「审核」（只管新建库与非空 `task_types` 的新用户）；
     **存量用户的 `task_types` 里不会自动多出这一类**——认领方若显式传了 `task_types` 白名单就会漏领审核任务。
     处理：设置页的 `task_types` 词表加「审核」（不自动改存量值，避免「我的词表被应用改了」），并在手册与派生评论里写明
     「审核任务的类型是『审核』，认领方的 `task_types` 别把它滤掉」；空数组=不限，是脚本的缺省形态（现有 `cursor-agent-poll.mjs` 就没传）。
   - 词表面：`get_vocabulary` 的 `review_mode.semantics.auto` 改成「派生一支『审核』类型任务进待执行，由非执行者 Token 经
     **常规认领链路**领取；结论经 `complete_task` 的 `review_verdict` 回落」，并新增 `review_verdict` 一节。
     MCP 工具表少两行（`claim_next_review` / `submit_review` 退场）。

6. **可见面（不加熔断，与 Q5=A 一致）**
   - 被审任务卡片：现状的「等待自动审核」角标语义改为「已派审核任务 T-1012」，点开能跳到那支任务；
   - 审核页顶部一行「自动轨 N 支 · 最近一次审核器活动 T」（T 取自 `reviews` 里最新的 `reviewer_type=agent` 行，零新列零计时器）；
   - 审核任务在看板上就是一支普通 READY 卡，类型徽标显示「审核」——**它就该被看见**，这是 P2 的可见性回报。

7. **脚本形态（零依赖，因为不需要新通道）**
   `scripts/review-agent-poll.mjs` 与现有 `cursor-agent-poll.mjs` 同族，且比它更薄：走的就是
   `POST /api/v1/tasks/claim`（现有路由）→ `ATB_EXEC` 跑无上下文干净会话 → `POST /api/v1/tasks/:id/complete` 带
   `review_verdict`。CLI 输出解析不出结论、或超时/非零退出 → 走 `fail`（结论宁缺不代拟）。
   `task_types` 环境变量沿用现有约定，缺省不传（=不限）。

8. **通知**
   两枚 kind 保留、语义微调：`review_auto_pending` = 审核任务已派生、在等认领；`review_auto_passed` = 审核任务回落 APPROVE。
   ESCALATE 走现状 `review_pending`（那条才是在等人）。

## 4. 与上一版的差异（推翻清单）

| 上一版 | 本版 |
|---|---|
| 专用队列工具 `claim_next_review` / `submit_review`（MCP-only，无租约、不占位） | 删除。审核走 `claim_next_task` + `complete_task`，天然带租约与幂等 |
| Q2 曾需在「补两条 agent-scope REST」与「脚本引 MCP SDK 破零依赖」之间取舍 | 该分叉**消失**——认领与回写两条路由今天就在 Agent 面上 |
| 证据靠给 agent 开产物读面（或内联）的选择题 | 统一为「证据随任务下发」，鉴权面零改动 |
| rubric 三选（技能 / 常量 / 不做） | 定死走技能（P3），设置键 `review_rubric_skill` 可指向用户自写的那条 |
| 载荷要新增 `review_rubric` / `artifacts[].uri` / 内联正文等专用字段 | 都不需要——审核任务就是普通任务，证据在 `description`，判据在 `skills` |
| 新增「领取上下文」以支撑窄口产物读（把队列做重） | 不需要，租约机制已经覆盖了「谁在做这件事」 |

## 5. 待拍板（本版只剩三题）

- **Q1 审核任务是否默认进认领池**：A（推荐）`status=READY` 立即可领；
  B `status=BACKLOG`，由人点「确认可执行」才放行（多一道人工闸门，但「自动」名不副实，且与 Q1 09-28 的 opt-in 裁定重复设闸）。
- **Q2 `review_mode` 与审核任务的关系**：A（推荐）`auto` 保留为派生开关，`review_track` 语义随之改为「有审核任务在跑 / 等人」；
  B 干脆取消 `auto` 这个中间值——用户直接建一支审核任务（更显式，但每个要审的任务都得手建两支，日常成本压回用户）。
- **Q3 存量 `task_types` 里加不加「审核」**：A（推荐）不自动改存量，只在设置页词表里可加，文档写明滤掉就领不到；
  B 迁移 0021 顺手给所有存量 `task_types` 追加「审核」（省事，但平台替用户改了词表）。

## 6. 非目标

- 平台侧起任何进程、任何模型调用、任何出本机的网络请求。
- 平台侧代 agent 判断「这轮审核该不该过」，包括任何形式的默认通过。
- 超时定时器、积压熔断、自动整池转人工（Q3 09-28 裁定：行为可预期优先于自动兜底）。
- 给 Agent 开放产物正文读接口（本版把证据改成随任务下发，鉴权面零变更）。
- 审核任务的二级复核（审核任务自己再被审）。

## 7. 验收要点（拍板后补细节）

1. `review_mode=auto` 的任务 complete 后：被审任务落 REVIEW/track=auto **+** 审核任务落 READY，两者同事务，无半态。
2. 执行者 Token 领不到那支审核任务（认领侧过滤命中）；换一个 Token 领得到；人手工把审核任务派给执行者时提交侧 403 仍生效。
3. 审核任务 `complete` 不带 `review_verdict` → 422；带 APPROVE → 被审任务 DONE + reviews 行署名 `agent · <Token 名>` + 推 `review_auto_passed`；带 ESCALATE → 被审任务 track=human + 推 `review_pending`，且此后不再被领。
4. 审核任务自身 DONE，永不进 REVIEW（无递归）；被审任务卡片能跳到审核任务，审核页「最近审核器活动」随结论落库而更新。
5. 存量库迁移演练（/tmp 副本 + `ATB_DATA_DIR`）：0021 两列 + 索引就位，存量任务 `review_of_task_id` 为 NULL，词表未被平台改写。
6. 零依赖脚本全链路（假 CLI 夹具）：通过 / 驳回 / 解析失败→fail 三态各一次，断言平台侧**没有**任何代拟结论。
7. 回归须主动查：新增的 READY 卡会不会把「待执行」列撑爆、`board?requirements` 完成度是否被审核任务算进去、筛选与分组视图里审核任务的归属显示是否正确。
