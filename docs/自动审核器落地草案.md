# 自动审核器落地草案 · 第四版「审核批次任务 + 审核回路」（2026-09-29 讨论稿）

> 状态：**待用户审核**，本版为最新权威版（前三版在 git 历史：`2603bce` 审核即任务、`26d1384` 批次+回路、及其前的专用队列版）。
> 本版依据用户 2026-09-29 三点裁定重写：
> ① **不考虑历史数据**（迁移可干净重做，不写兼容与回填）；
> ② 审核是一个**特殊任务**，它专门审核**一个或多个**任务；
> ③ 审核任务与被审任务之间形成**回路（loop）**，且**可配置上限**。
> 第四版追加裁定 ④：**新增一个类型为「审核」的任务**，并把**交互设计写全**——本版 §5 整章重写，每条都带前端落点。
> 设计公理沿用上版 P1–P5：平台只存储 / 下发 / 回写，**一切工作皆任务**，技能随任务下发，平台不起进程、不设计时器。

## 1. 主模型（一句话）

`review_mode=auto` 的任务完成回写后，不再等平台侧的审核队列，而是**由平台派生一支「审核」类型的任务**：
它声明覆盖 N 支被审任务，等到这些任务里**有任意一支进入「待审核」**就被激活进待执行，
被任何**非执行者** Token 经常规认领链路领走、审完回写结论，
平台按结论分别流转各被审任务，并决定这支审核任务**回待执行跑下一轮**还是**落已完成收工**——
轮次与批次容量都是设置键，触顶就整批转人工。

## 3. 数据模型

### 3.1 「审核」任务（0929 裁定新增类型）

一支普通 `tasks` 行，靠三个特征成为特殊任务：

1. **`type = '审核'` 进 `DEFAULT_TASK_TYPES`**（`apps/api/src/contract/enums.ts:226`，现值 需求/缺陷/子任务/巡检/重构）——
   这是用户 0929 的裁定，产品叙事上「审核是一种任务」必须在类型词表里看得见；
2. **`review_batch` 新列（迁移 0021）才是行为判据**：`INTEGER DEFAULT 0`，`1` = 这支是审核批次任务。
   为什么不能只看 `type`：类型是设置页可增删的自由词表（`settings/tabs/general.tsx:99-117`，上限 16 项），
   把回路行为钉在自由词表上，用户删掉「审核」这个词就把已在跑的批次打断；
   前端同样按 `review_batch` 判图标与配色（§2：今天没有 type→图标映射，也不新建词表化的映射）。
3. `review_mode = 'none'`——审核任务自己不进审核，否则无限递归（`none` 在这里的含义是「它的 complete 就是结论落地」）。

**「有类型不等于有批次」的三档身份（交互上必须分得清，见 §5.1）**：

| 身份 | 判据 | 从哪来 | 能不能审别人 |
|---|---|---|---|
| 批次任务 | `review_batch=1 ∧ type='审核'` | §5.5 自动挂批 / §5.6 打包送审 | ✅ 能，且这是它唯一用途 |
| 「审核」类型的普通任务 | `review_batch=0 ∧ type='审核'` | 人在建单面手选这个类型 | ❌ 不能——它只是给人工整理的分类 |
| 其它类型任务 | `review_batch=0` | 常规建单 | ❌ 不能 |

> 第二档是本设计**故意保留的口子**而不是缺陷：手建一张空批次既没有覆盖对象、也没有判据技能，
> 只会造出一个永远不可领的死卡（§4.2）。所以建单面选了「审核」类型时，就地提示
> 「这个类型只是分类；要让 Agent 审核任务，请在待审核队列里**打包送审**」（§5.16 文案 ①）。

### 3.2 覆盖关系：第三种依赖边 `review`

- `task_dependencies` 的 `type` CHECK 扩为 `('blocks','relates','review')`（0001 建表法需整表重建，照 0018 教训保住既有索引）。
- 方向：`审核任务 T-a` 的边指向 `被审任务 T-b`（`task_id = T-a, depends_on = T-b, type='review'`），N 条边 = 审 N 支。
- **不参与**环检测与认领过滤（与 `relates` 同级）：它只是归属声明，激活靠下面 §4 的状态动作，不靠依赖解锁。
  这条是本版与用户原话唯一有出入的地方，理由见 §2 第一行的死锁。
- 反查「这支任务被哪个批次覆盖」：`WHERE depends_on = ? AND type='review'` 一条索引查询。

### 3.3 轮次与批次上限（两个新设置键 + 一列）

| 键 / 列 | 默认 | 含义 |
|---|---|---|
| `tasks.review_batch`（列，0021） | `0` | 标记这是审核批次任务 |
| `review_batch_max_targets`（设置） | `5` | 一支批次最多覆盖几支被审任务（建批与追加时校验） |
| `review_max_rounds`（设置） | `3` | 回路最多跑几轮；比较对象是批次任务的 `run_count` |
| `review_auto_dispatch`（设置） | `true` | `complete` 分流是否自动挂批次（关掉＝只允许人工打包） |

### 3.4 判据（rubric）

做成一条内置默认技能「自动审核判据」（分类 `编码开发 / 质量与安全`，随包发布、`SKILL_READONLY`），
建批次时绑到批次任务的 `skills` 上 → 认领载荷 `AgentTaskPayload.skills` 自动把正文带下去（技能随任务下发，公理 P3）。
新设置键 `review_rubric_skill` 可指向用户自写的技能。

## 4. 生命周期与回路（本版核心）

### 4.1 状态动作序列

```
被审任务 T-b（review_mode=auto）
  complete_task ─┬─→ T-b: RUNNING → REVIEW / review_track=auto
                 └─→ 平台同事务【挂批次】：
                      已有可复用批次？
                        ├─ 是 → 给该批次补一条 review 边（覆盖数 ≤ review_batch_max_targets）
                        └─ 否 → 新建批次 T-a（type=审核, review_batch=1, review_mode=none,
                                      status=BACKLOG, skills=[判据技能], 证据写进 description）
                      若 T-a 处于 BACKLOG → 立刻 BACKLOG → READY（激活）

批次 T-a（READY，在认领池里）
  claim_next_task（任何非执行者 Token；租约/幂等沿用现状）
    认领侧过滤：批次内**全部**被审对象都不在「可审」状态时，跳过该候选（见 4.2）
  → RUNNING，agent 审完
  complete_task（带 review_verdict，见 §6）
    ├─ 平台按 verdict 逐支流转被审任务：APPROVE → DONE；REJECT → READY/BACKLOG；
    │   未给结论的 → 原样停在 REVIEW/track=auto
    ├─ 回路判定：仍有被审对象处于 REVIEW/track=auto（或后续会再回来）
    │      ├─ T-a.run_count < review_max_rounds → T-a: RUNNING → READY（下一轮，run_count 已在认领时 +1）
    │      └─ 触顶 → 剩余对象全部 track=human + 推 review_pending，T-a → DONE，评论记「轮次耗尽转人工」
    └─ 全部对象已落定（DONE 或已被人接管）→ T-a → DONE
```

**「激活」为什么不靠依赖**：被审任务停在 `REVIEW` 不是 `DONE`，`blocks` 边会让批次永远进不了池（§2）。
改用**状态动作**表达用户的原话——「a1、a2 进入待审核状态后 a 就启动激活」＝
被审任务 `complete` 落 REVIEW 那一刻，平台把覆盖它的批次从 BACKLOG 推到 READY。
平台做的是一次**状态流转**（现有流转，`BACKLOG→READY` 是已验收动作），不是判断，完全在 P1 之内。

### 4.2 「可审」判定与认领侧过滤

批次任务对认领池的可见性条件（`CANDIDATE_SELECT` 给 `review_batch=1` 的行加一条 EXISTS）：

- 至少一条 `review` 边指向的任务满足：`status='REVIEW' ∧ review_track='auto' ∧ archived_at IS NULL`；
- 且该对象被审 Run 的执行者 Token ≠ 调用方（自审门禁，换到认领侧：自己干的活不派到自己面前）。

两者都不满足时，批次**不进候选**（不报错、不占坑）——被审任务还没跑完，或全被人接管了。

### 4.3 人接管（「转人工审核」在批次语义下）

单支被审任务点「转人工审核」＝ `review_track=human`（现有实现），它自动不再满足 4.2 的「可审」判定，
于是从批次里**自然脱出**——不删边（历史可追溯）、不需要新端点。
全部对象都被接管时，批次不再可领，卡片显示「无待审对象」空态（§5.3）；人的出路是矩阵里现成的
✅「撤回」（READY→BACKLOG），批次回到需求池等着被 §5.5 的挂批复用，或在危险操作里删除。

### 4.4 失败与租约

- 批次任务 `fail_task` / 租约过期 → 沿用现状（`FAILED`、可重试），被审任务留在 `REVIEW/track=auto`；
- 平台**不重试、不计时**（0928 Q3 裁定不动）；重试=人点重试或外部调度再领。

### 4.5 批次自己的收工（为什么不新增流转）

批次任务 `review_mode=none`，所以它的 complete 落点**天然就是 DONE**（0020 已实现的三分流），
三种收工场景都不需要新的状态流转：

| 场景 | 谁写的 DONE | 备注 |
|---|---|---|
| 全部对象本轮落定 | 本轮 `complete(review_verdict)` 的尾部动作 | 与 4.1 最后一支同事务 |
| 轮次触顶 | 同上（触顶分支：剩余对象 `track=human` + 批次 DONE + 评论留痕） | Q3 推荐 A |
| 对象全被接管、批次空转 | **不写 DONE**，留在 READY → 人「撤回」到 BACKLOG | 矩阵 `READY→DONE` 是 ❌（§2），不设「人工结案」按钮 |
| 批次执行失败 / 租约过期 | 不写 DONE，落 `FAILED`（沿用 4.4） | 人「重试」回 READY 即下一轮 |

> 这一条是第四版对第三版的**自我修正**：上版 §5.2/5.4 给批次设计了「结案」按钮，
> 那是往七列矩阵里塞一条新流转，踩 0020 的非目标线。本版按「不新增流转」重做（§5.3 动作矩阵）。

## 5. 交互设计（第四版整章重写）

**本章的唯一验收标准**：自动轨任何时候都不是黑箱——人能立刻回答三问：**谁在审** / **审到第几轮** / **结论在哪**。
下面每条设计都指向这三问之一。所有措辞收在 §5.16 一张表并进 `apps/web/src/lib/copy.ts`，
别处不得自拟（手法与 `board/matrix.ts:12` 的「前端不得再写一套 `to:` 字面量」同一条）。

### 5.1 三档身份在界面上怎么区分（§3.1 那张表的视觉版）

| 身份 | 卡片呈现 | 落点 |

| **批次卡**（`review_batch=1`） | header 徽标行加 `Scale` 图标 + 类型 Badge「审核」；标题下第一行是**覆盖短号列表**（`T-1008 T-1012 +1`）；标题右侧**轮次 pill** | 徽标行 `task-card-view.tsx:125-131`、类型 Badge `:140`、短号行插在标题 `:137` 之后（现有 tags 位 `:144-147` 之上） |
| **被审卡**（`status=REVIEW ∧ track=auto`） | 现有 `ReviewBadge`（Bot=等 Agent 审 / Bell=等你，`board/model.ts:144-164`）**形状不动**；其下加一行来源 `由 T-1050 审 · 第 2/3 轮`，短号可点 | 来源行与批次卡短号行同一位置；跳转用 `useShellStore.openTask(batchId)`（`app/store/shell.ts:68`，抽屉可叠加，`overlay-slot.tsx:33`） |

  批次语义下人是「等哪一支批次」，不是「等某个 Token」→ 文案 ⑭；label `等待自动审核` 四字保留（0020 已验收的措辞，别顺手改）。

  `apps/web/src/lib/task-icon.ts`，只按 `review_batch` 返回图标，不接自由词表。
- **不给批次另配一套颜色**：配色已全部分给 status（`lib/status-style.ts:18-73`）与 priority（`:81-92`），
  再给类型上色会让人把批次卡误读成一种新状态；批次只靠图标 + pill + 文案区分。

| 列 | 批次卡出现条件 | 卡片文案（逐字，见 §5.16） | 说明 |
|---|---|---|---|
| 需求池 `BACKLOG` | 建批即未激活 | `审核批次 · 覆盖 2 支 · 等待审核对象进入待审核` | 派生即建但还没激活的批次必须看得见，否则用户以为「建了个死任务」 |
| 待执行 `READY` | 有 ≥1 支可审对象 | `审核批次 · 覆盖 3 支 · 第 2/3 轮待领取` | 不进认领池的（对象全被接管）也显示在同一列，靠下面的空态区分 |
| 待执行 `READY`（空） | 覆盖对象全部落定/被接管 | `审核批次 · 无待审对象（3 支已全部落定或转人工）` | 没有任何 Agent 会领它；出路见 §5.3 |
| 执行中 `RUNNING` | 被领取 | `审核批次 · 第 1/3 轮 · 进行中` + 现有进度体（`:179,331-365`） | 轮次就是本轮 Run，不另造计数 |
| 待审核 `REVIEW` | **永不出现** | — | 批次 `review_mode=none`，complete 直接落 DONE（§4.5） |
| 已完成 `DONE` | 收工 | `审核批次 · 已完结 · 通过 2 / 驳回 1 / 转人工 0` | 汇总数字来自 `reviews`，零新列 |
| 异常 `FAILED` | 某轮执行失败 | `审核批次 · 第 2 轮失败 · 已执行 2 次` | 被审任务仍停在待审核（4.4） |

**轮次 pill 的取值口径**（`run_count` 在认领事务里 +1，`claim.service.ts:145-162`，所以「已领次数 = 已跑轮次」）：

| 卡片态 | `run_count` | pill 文案 | 色调 |
|---|---|---|---|
| `READY` 从未领取 | `0` | `未开始 · 最多 3 轮` | neutral |
| `RUNNING` 第 1 轮 | `1` | `第 1/3 轮` | neutral |
| `READY` 上一轮回来 | `1` | `第 2 轮待领取 · 共 3 轮` | neutral |
| `RUNNING`/`READY` 且 `run_count == max-1` | `2`（max=3） | `第 3/3 轮即将开始` | **warning** |
| 本轮 complete 后 `run_count == max` | `3` | 触顶分支：平台直接写 DONE，卡片不再回 READY | — |

醒目规则：`run_count ≥ max-1` 起 pill 换警示色，且**不能只靠颜色**（附文字「本轮结束后剩余转人工」）。
控件复用 `Badge`（`components/ui/badge.tsx:33`）与 `RequirementBadge` 的计数 pill 形状（`features/requirements/requirement-badge.tsx:34`）。

**列污染取舍**：批次卡会占「待执行」列，且列头计数会含它（`board-column.tsx:182-186` 的计数 pill 不隐藏批次——藏计数比多一张卡更糟）。
过滤走**全局筛选维度**（列头没有列内筛选，§2），见 §5.11。这条挂 Q4。

### 5.5 入口 A：自动挂批（用户无感，但痕迹必须看得见）

挂批的**复用键**（Q1 的聚合口径，本稿按 `parent_task_id` + `group_id` 双键、组内取最近活跃批次）：
同一分组/需求下、`status ∈ {BACKLOG, READY, RUNNING}`、覆盖数 `< review_batch_max_targets` 的批次里取 `updated_at` 最近的一支；
没有就新建。这样被驳回→重跑→再回 REVIEW 的对象会**回到同一批次**（口径与 §5.4「重跑后回到批次」对齐），
回路才是「一个批次多轮」而不是「一轮一个批次」。

用户虽不操作，但要在四处看到发生过什么：

1. **被审卡来源行**（§5.4）；
2. **批次卡覆盖数变化 + 由需求池跳到待执行**（`task.created` / `task.moved` 现成帧，§2）；
3. **通知**（§5.12 文案，带批次短号与轮次）；
4. **评论双向留痕**：批次评论 `T-1012 由完成回写自动挂入本批次（第 1 轮）`；
   被审任务评论 `已进入自动审核批次 T-1050（第 2 轮）`。

`review_auto_dispatch=false` 时 complete 只落 `REVIEW/track=auto`、不建批；此时待审核列与审核页出现引导位（§5.10）。

### 5.8 批次详情抽屉（信息密度最高的一屏）

抽屉是 `task-detail/index.tsx`（body `:77`、Tab 条 `:93-96`、FooterBar `:151-177`），批次复用同一个壳，不新建页。

1. **标题行**：`Scale` 图标 + `审核批次 T-1050` + 轮次 pill + 一枚中性 Badge `免审核（结论即回写）`
   ——这枚必须有，否则人看到「批次自己不进审核」会当成漏洞（§3.1 第 3 点）。
2. **概览 Tab 首屏 = 「审核对象」区**（顶到普通任务的字段表位置）：
   列 = 短号（链）/ 标题 / 状态 / `track` / 本轮结论 / 累计结论数 / 执行者；
   行右 = `从批次摘出`（仅未落定行可用）；区右上 = `添加审核对象`；
   数据源新增读面 `GET /tasks/:id/review-batch`（一次给批次信息 + 对象数组 + 每对象最新 verdict），
   **不在 `GET /tasks/:id` 里塞嵌套**——沿本项目「事件与读面带定位字段、列表回 GET 拿真相」的读取模型（`api/types.ts:990-998` 头注释同一条理由）。
3. **「审核」Tab 对批次改名 `本批次结论汇总`**（Tab 名在 `task-detail/labels.ts:15-23`，需按 `review_batch` 走条件分支）：
   逐轮一行 `第 1 轮 · 09-29 12:04 · 通过 2 / 驳回 1 / 未判 0`，展开看 `report` 全文与逐支结论，
   每条链到被审任务「审核」Tab 的记录锚点；批次自己的 `reviews` 表**恒空**（没有人为它写结论）。
4. **「执行」Tab 不变**：批次的每个 Run 就是一轮审核，`summary` 带 report，日志与产物沿用现有面板。
5. **「技能」Tab**：显示判据技能，行内 `换判据` 只在 `BACKLOG/READY` 可用；`RUNNING` 中禁用并提示
   `本轮已按当前判据领取，中途换判据会让这一轮的口径漂移`。
6. **空态**：`BACKLOG` 未激活 → `等待审核对象进入待审核；现在不会有任何 Agent 领取它`（不是错误，别用红色）。
7. **危险操作**：删除仍有 `track=auto` 覆盖对象的批次时，确认文案必须点明后果：

### 5.14 给 Agent 的界面（审核器的交互设计也是交互设计）

批次被认领后 Agent 看到的载荷形状在 §6，这里定**它读到什么文字**：

- `description` 不是人写的正文，而是平台生成的**批次说明 + 逐支证据块**；
- `skills=[判据技能正文]`（公理 P3：技能随任务下发）；
- `review_targets[]` 每支给 `id/title/status/track/run_id/evidence`；
- `get_vocabulary` 的 `review_verdict` 段告诉它输出形状，并新增一段 `review_batch` 语义：
  **拿不准就 `ESCALATE`，不要硬猜**；给不出结论不是失败，是转人工的正常出口。

证据块格式定死（写进 vocabulary 与使用手册，避免每个 Agent 自拟一套）：

```
【审核对象 T-1012 · 第 2 轮 · 批次 T-1050】
标题 / 执行者 Token / 回写时间 / 上次结论（REJECT：三字段摘要）
本次 summary（≤20000，原样搬运）
日志尾段（最近 50 行）
产物清单：type · 文件名 · uri ·（≤64KB 的文本类正文内联，其余只给 uri）
```

## 10. 验收要点

**回路正确性**

1. 被审任务 `complete` 后同事务出现批次（或挂进已有批次），批次由 `BACKLOG` 即刻 `READY`；断言不存在「批次永远领不到」的死锁路径。
2. 执行者 Token 在池里看不到唯一对象是自己跑的那支的批次；换 Token 立即可领。
3. 一轮 `complete(review_verdict)` 后：APPROVE 支 DONE、REJECT 支回 READY/BACKLOG、未判支留 auto；批次按 4.1 判定回 READY 或 DONE，`run_count` 与轮次文案一致。
4. 触顶（`run_count == review_max_rounds`）时剩余对象整批转人工 + 推 `review_pending` + 批次 DONE + 评论留痕；
   且**断言批次落 DONE 没有走任何新的流转端点**（矩阵快照不变）。
5. 人点「转人工审核」后该支从批次脱出（4.2 判定不再成立）；批次失去全部对象后不可领、卡片显示 §5.2 的空态、唯一出路是「撤回」。
6. 被驳回→重跑→再回 REVIEW 的对象**回到同一批次**（§5.5 复用键），不是一轮一个批次。

**交互面**

7. DAG 里 `review` 边是第三种线型（点线），**两处渲染点**（`DependencyGraphCanvas.tsx:352-362` 与 `flow/DependencyEdge.tsx:32-43`）都生效；可加可删；删边只脱批、不改 `track`。
8. 批次任务的 `skills` 载荷带判据正文；`review_rubric_skill` 改指用户自写技能后载荷随之变化，且 `RUNNING` 中改判据被禁（§5.8 第 5 点）。
9. 三处入口的可达性各测一遍：自动挂批（无操作）、审核页多选打包、任务列表批量条打包、批次菜单追加对象；
   置灰行必须带原因文案（不允许静默过滤）。
10. 批次卡上看不到「审核通过/驳回」菜单项（§5.15 第一条），批次自己的 `reviews` 表恒空。
11. 「摘出」「转人工」「删除批次」三个动作的后果文案互不相同且各自准确（§5.7）——这是最容易被实现成同一句的一组。
