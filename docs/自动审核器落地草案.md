**设计公理（P1–P5，本方案的唯一裁判尺度）**

- **P1 平台是看板不是执行者**：只存储 / 下发 / 回写，不评估内容、不代拟结论。
- **P2 一切工作皆任务**：Agent 干的每件事都走「任务 → 认领 → Run → 回写」这一条通路，不存在第二类工作。
- **P3 技能随任务下发**：判据/规范通过 `skills` 载荷下去，不给 Agent 开新的读取面。
- **P4 Agent 凭证面只有 tasks 那一条通路**（15 章 UI-only 铁律）。
- **P5 平台不起进程、不设计时器**。

## 1. 主模型

`review_mode=auto` 的任务完成回写后，平台不为它起任何队列，而是**派生/复用一个「审核批次任务」**：

1. 批次是一支普通任务，`review_batch=1`、类型词表里的 `审核`，**覆盖 1..N 支被审任务**（N 条第三种依赖边）；
2. 被审对象进入「待审核」的那一刻，平台在**同一事务**里把它挂进同桶最近一支可复用批次，并把批次从 `BACKLOG` 推到 `READY`；
3. 任何**非执行者**的 Agent Token 经常规 `claim_next_task` 领走它，判完用 `complete_task` 带 `review_verdict.items[]` 回写；
4. 平台按结论逐支流转被审任务（同一份 `submitReview` 实现），再按事实分流：本轮有结论生效且仍有可审对象 → 批次回 `READY` 跑下一轮；否则落 `DONE`；
5. **轮次预算记在被审对象身上**（该对象的 Agent 结论数），不在批次身上——批次 `run_count` 只作「已执行几次」展示。

一句话不变式：**平台只做三件事——挂批（建边）、推状态（激活 / 回 READY / 落 DONE）、按 verdict 搬运结论。三件事都是既有动作形状。**

### 3.2 覆盖关系：第三种边 `review`

- `task_dependencies.type` CHECK 扩为 `('blocks','relates','review')`；整表重建（0018 法）并保下全部既有索引
  （`idx_deps_task`、`idx_deps_depends_on`，`0001_init/migration.sql:47-48`）与 `UNIQUE (task_id, depends_on)`。
- 方向：`批次 T-a → 被审 T-b`（`task_id=T-a, depends_on=T-b, type='review'`），N 条边 = 审 N 支。
- **纯标记边**：不参与认领过滤、不参与环检测（与 `relates` 同级的处置，实证见 §2 第 1/3 行）。
- 反查「这支被哪个活跃批次覆盖」：`depends_on=? AND type='review'` JOIN 批次侧 `status != 'DONE' ∧ archived_at IS NULL`。
- **唯一活跃覆盖约束**（N16）：同一对象最多被一支未结案批次覆盖；违反 → `409 ALREADY_IN_ACTIVE_BATCH`，
  UI 侧对应 §5.6 的「换批」勾选（删旧边 + 建新边）。SQLite 表达不了带 JOIN 的部分唯一索引，**校验落在代码**（事务内 count）。
- ↑ 这道校验**对人工建的 `review` 边同样生效**（N33）：REST `POST /tasks/:id/dependencies` 与 §5.12 的 DAG 加边下拉
  自 0021 起也能写 `review`，所以校验收在**共享的加边实现**里（`tasks.service.ts` 的 `addDependency` 一条），
  不得只在 `ReviewBatchService` 里写一份。人工边只是标记边：不解锁认领、不生成 `review_targets`、
  不影响批次载荷——人要给某支任务派审核工作仍走 §5.6 打包送审。
- 边的生命周期：对象被驳回 → 重跑 → 再进自动轨时，**同一批次同一批边继续用**（§4.3 复用键），不重复建边；
  对象转人工/落定不删边（track 变化即自然脱批，边只是归属记录）。

### 3.3 轮次预算：记在被审对象身上（本版核心修正）

| 量 | 算法 | 用途 |
|---|---|---|
| 对象已用轮次 `used` | `COUNT(reviews WHERE task_id=obj AND reviewer_type='agent')` | **预算判定**：`used ≥ review_max_rounds` → 该对象此后的完成回写不再进自动轨，直接 `track=human` |
| 对象当前轮 | `used + 1`（展示用） | 文案 `第 {used+1}/{max} 轮`；`used ≥ max` 时改显示 `自动审核已用尽`，**不得出现 `第 4/3 轮`**（N25） |
| 批次执行次数 | 批次自身 `run_count` | 仅展示 `已执行 {run_count} 次`，**不参与任何判定** |

**为什么必须记在对象侧**（C2）：预算记批次 `run_count` 时，触顶后批次 DONE、被驳回对象重跑回来按复用键**另建新批次**、计数归零——
「最多 3 轮」变成「每轮重建一次预算」，成本上限形同虚设。记对象侧后无论批次怎么新建、对象怎么重跑，Agent 为同一支任务出的结论总数封顶。

- **`ESCALATE` 不写 `reviews` 行**（沿用 0020 的 escalate 只换轨不写结论），所以「审核器知难而退」不消耗预算——它直接让对象离开自动轨，比消耗预算更彻底。
- **人抢审/人审不消耗**：人不占 Agent 预算。
- **批次归属另需一列**（N20）：`reviews.run_id` 语义是「被审的那次 Run」，不能挪用。§5.7「逐次执行汇总」与
  §5.4「第 n 轮 · 由批次 T-1050 审」都需要反向指认「这条结论是哪支批次的哪一次 Run 给的」→
  迁移 0021 给 `reviews` 加 **`reviewer_run_id TEXT`（可空，人审为 NULL）+ `idx_reviews_reviewer_run`**。
  Agent 逐支落地时填**批次的 Run id**；批次抽屉按它 `JOIN task_runs ON task_runs.id = reviews.reviewer_run_id WHERE task_id=批次` 分组，
  对象侧按它反查批次短号（`run.task_id`）。预算计数仍只用 `task_id + reviewer_type`，与这列无关。

### 3.4 判据与证据

- 判据默认绑既有内置技能 `skl_builtin_code-review`（分类 `质量与安全`，已随包发布、只读），
  由建批时写进批次任务的 `skills` → 认领载荷自动带正文（P3）。新键 `review_rubric_skill` 可改指任何技能，`''` = 不绑。
  **不新增内置技能**（N14，避开 124/125 锁与 `.md`/分片/回填链）。
- 证据只在认领载荷 `review_targets[].evidence` 里，**不写进 `description`**（N3）。
  `description` 只放批次说明（人可读）：覆盖短号列表、判据名、本轮待判数。
- 证据体积是**常量**不是设置键（N4）：`summary` 截 2000 字符、日志尾段 ≤50 行且 ≤8000 字符、
  产物仅 `type ∈ {text,markdown,json,log,diff}` 且 ≤16KB 时内联正文（diff 取前 200 行），整批 ≤64KB；
  超出置 `truncated: true` 并只给 `uri`。给不下的部分 Agent 可以判 `ESCALATE`，平台不替它补。
  既有 `REVIEW_LOGS_PAGE_SIZE=200` 是单任务队列的口径，搬进批次载荷时**另立常量 50**，别原样带过来（N28：5 支 × 200 行必爆 64KB）。
- 组装成本：每支对象一次 `runLogs` + 一次产物清单，N ≤ `review_batch_max_targets`(5) 且只在**认领时**算，
  载荷组装走既有 `AgentQueryService.payload` + `TasksService.runs/runLogs`，不新写查询（N9）。

### 3.5 四个设置键（进 `DEFAULT_SETTINGS`，落点 `contract/settings.ts:30-39` 一带）

| 键 | 默认 | 语义 |
|---|---|---|
| `review_auto_dispatch` | `true` | `false` 时 complete 只落 `REVIEW/track=auto`、不建不挂批次（全手动打包） |
| `review_batch_max_targets` | `5` | 一支批次最多覆盖几支（建批与追加都校验，事务内 count） |
| `review_max_rounds` | `3` | **对象级** Agent 结论数上限（§3.3） |
| `review_rubric_skill` | `'skl_builtin_code-review'` | 建批时绑到批次 `skills` 的技能 id；`''` 不绑 |

四个键在 complete 分流前一次性取齐（C9）。改动只作用于**之后新建/追加的批次与该批次的后续轮次**，已在跑的批次本轮口径不变。

## 4. 状态机与回路

### 4.1 complete 的分流优先级

```
POST /tasks/:id/complete（Run 归属校验、租约校验、幂等 replay 沿用现状）
 ① review_batch = 1                → 走批次分支（§4.2），要求必带 review_verdict
 ② review_mode 解析（现状 resolveReviewMode 不动）
    human → REVIEW / track=human + review_pending
    auto  → REVIEW / track=auto，然后：
            对象预算已耗尽(§3.3) → 直接 track=human + review_pending（不建批）
            review_auto_dispatch=false → 停在 REVIEW/track=auto（等打包）
            否则 → §4.3 挂批（同事务）
    none  → DONE + 现文案「免审核直通」
 ③ 分支 ① 的留痕不走 ②（批次评论写「审核结论回写（批次 T-x 第 R 轮）」，不写「免审核直通」）（C3）
 ④ 通知在分流结局定下之后（事务外）推**且只推一条**（N31）：
    挂批成功 → review_auto_pending（文案带批次短号与轮次）；dispatch=false 未挂批 → review_auto_pending（现文案）；
    预算耗尽转人工 → review_pending。现状那个写死的 push（writeback.service.ts:329）改成按结局选文案，不得各推一条。
```

`review_mode='none'` 在批次上只是短路标记，`directTo` 计算与 `mode==='none'` 的直通后置链（解锁 + `task.moved`）不得为批次执行——
批次不是被审对象，它没有「免审核直通过」这回事。

### 4.2 批次的回写：落点、两阶段与竞态（本方案唯一新增的落点）

**落点**

- 批次 complete 的落点集合加一条：`RUNNING → READY`，**仅当 `review_batch=1` 且本轮有结论生效且仍有可审对象**；其它任务给这个落点直接 `409`。
- 4.5 人拖拽矩阵**一格不加**（前后端两张表逐格仍一致，矩阵快照测试不改），改动只在 `writeback.service.ts` 的落点选择里——
  措辞统一为「Agent 回写落点表新增一行」（C1）。

**两阶段（N18，硬约束）**

```
阶段一（现有 complete 事务内，不新增事务）
  1. 关 Run（SUCCESS + summary=report）、批次 lease 清理，沿用现状
  2. 校验 review_verdict：items 逐条 id ∈ 本批次覆盖边、非 self → 否则整批 422（见下）
  3. 批次状态**先不动**（保持 RUNNING），事务提交
阶段二（事务外，逐支顺序执行）
  4. 对每条 item 重读对象快照：status='REVIEW' ∧ review_track='auto' ∧ 边仍在本批次 → 不满足则记入 skipped[]，继续下一条
  5. APPROVE/REJECT → 调 `tasks.submitReview(objId, input, {type:'agent', name:Token 名})`，
     写 reviews 时带 `reviewer_run_id = 批次本次 Run id`
     ESCALATE → 调 `tasks.escalateToHuman`（不写 reviews 行）
  6. 全部执行完 → 按事实决定批次落点（§4.7），再一次写评论与审计
```

- **为什么必须分两阶段**：`submitReview` 自带 `$transaction`，且通知/解锁在事务外（§2 实证）。在 complete 的事务里调它 = SQLite 嵌套写事务，
  与 0020 那次「事务内读 settings 死锁」同一类锁等待，**不是风格问题**。
- **部分失败的恢复**：阶段二第 5 步抛错（如对象刚好被人拖走）→ 停止后续条目，响应给 `{applied:n, skipped:[...]}`，
  批次评论写「本轮生效 N 条，第 M 支回写失败：原因」；批次**停在 RUNNING**（Run 已关闭）。回收只有两条现成通路：
  人「强制停止」、或**既有租约回收定时器**（`lease.service.ts:73,183-215`）把它置 `FAILED`，再由 `FAILED→READY` 现成 ✅「重试」重领。
  重领时已落定的对象不再满足可审谓词 → 自愈，无需幂等表（沿用 `review-queue.service.ts:49-56` 的并发 ≤1 论证，不新造锁位）。

**竞态与错误码（N19）**

| 情形 | 处置 |
|---|---|
| `items[].task_id` 不属于本批次覆盖 | `422 VERDICT_TARGET_UNKNOWN`（编程错误，整批拒绝） |
| 条目对象是调用方自己跑的（self） | `422 SELF_REVIEW_FORBIDDEN`（沿用 0020 码，整批拒绝，避免半批生效） |
| 条目对象已被人转人工 / 已落定 / 已被摘出 | 进 `skipped[]`，**不报错**：结论本该作废，人已接手 |
| 缺 `review_verdict` | `422 VERDICT_REQUIRED` |
| `items` 为空数组 | 合法 = 本轮判定数为 0，触发 §4.7 第三行 |

**响应**：加 `next_round: boolean`、`round_targets_pending: number`、`applied: number`、`skipped: [{task_id, reason}]`，
Agent 侧据此决定要不要再来一轮（人侧不关心）。

### 4.3 挂批（建边 + 必要时建单 + 激活）

```
入参：待挂对象集合 [T-b…]（自动路径每批 1 支；打包路径 1..N 支）
1. 桶键 k = T-b.parent_task_id ?? '∅'                  （C4：不用 group_id；父只能是需求，§2 实证）
2. 取候选批次：review_batch=1 ∧ 同桶 ∧ status ∈ {BACKLOG,READY,RUNNING}
                ∧ archived_at IS NULL                  （N7：归档批次不得复用，否则黑洞）
                ∧ 覆盖数 < review_batch_max_targets
   → 有：取 updated_at 最近的一支；无：新建批次
3. 新建批次的字段：type='审核', review_batch=1, review_mode='none',
   status=BACKLOG, priority=min(本次对象的 priority)（N2；追加时取 min 重算一次，此后不追算，N27）,
   required_capabilities=''（任何 Token 可领）, origin_type='agent', origin_agent='review-dispatch',
   skills=[review_rubric_skill], description=批次说明, parent_task_id=k（∅ 桶则 NULL）
   ⚠ 批次与被审对象之间**绝不写 parent_task_id 互指**（§2：有子任务的任务不进池）
4. 加 review 边（先查 N16 唯一活跃覆盖；对象已被本批次覆盖则只跳过建边，其余步骤照常）
5. 激活：自动路径的对象刚落 REVIEW → 批次若为 BACKLOG 则 BACKLOG→READY；已在 READY/RUNNING → 不动。
   打包路径（§5.6）对象本就在 REVIEW → **新建批次直接落 READY**，不经过 BACKLOG（N23）。
6. 双向评论：批次侧「T-b 由完成回写自动挂入本批次 / 由人打包入批」；对象侧「已进入自动审核批次 T-a」
7. 通知不在这里推——由 §4.1 第 ④ 步在事务外推本次 complete 的**唯一一条**（N31），
   挂批成功时文案带批次短号与本轮轮次
```

- **并发与一致性**（C9/N8）：四个键在事务外取；建批与加边在写事务内，但**容量与唯一活跃覆盖的校验必须在事务内 `count`**，
  不能用事务外取到的快照；同桶的挂批动作按桶键串行化（先对批次行做一次条件 `updateMany` 占位再算覆盖数），
  避免两支对象同时 complete 造成重复建批或超容量。
- **RUNNING 中的批次被追加**（C8）：追加的对象**不进当前轮**——当前轮的 `review_verdict` 是 Agent 按领取时载荷写的，
  平台不回退批次、不重排载荷；批次卡显示 `本轮未覆盖 {M} 支`，追加对象等批次回 READY 的那一轮被判。
- 打包路径与自动路径**共用这一个函数**（入参只差对象集合与是否立即激活），不得写第二份挂批实现。

### 4.4 「可审」判定与自审

批次进认领候选的附加条件（给 `CANDIDATE_SELECT` 的 `review_batch=1` 分支加 EXISTS）：

- 至少一条 `review` 边指向的对象满足 `status='REVIEW' ∧ review_track='auto' ∧ archived_at IS NULL`；
- 且这些对象里**至少一支**的被审 Run 执行者 ≠ 调用方 Token（C5：任务粒度过滤只能拒「全部对象都是我的」）。

「被审 Run 执行者」= 对象的 `current_run_id` 那条 `task_runs.token_id`；**`token_id IS NULL` 视为无归属、可审**
（逐字沿用 `review-queue.service.ts:126-131` 既有口径，不新造语义；也不给 verdict 条目 `run_id` 位，防「指到别的 Run」绕开——N29）。

自审的三段式处置（C5）：

1. 认领：只拒「全部对象都不可自审」的批次；
2. 载荷：`review_targets[].self = true` 逐支标注不可自审，`get_vocabulary` 明说「这些跳过、别判」；
3. 回写：对 `self` 对象给结论 → `422 SELF_REVIEW_FORBIDDEN`（沿用 0020 错误码，不新增），未判对象自然留下一轮。

**单 Token 环境的死等是这套门禁的正确后果，不是漏洞**（N17）：只有一个 Agent Token 时，
它跑完的任务它对唯一的活跃批次不可领 → 自动轨永远不推进。平台**不检测、不豁免、不计时**（P5 + 0928 Q3 + 0020 Q4 硬线），
出路只有两条且都写进界面与手册：接第二个 Token，或人点「转人工审核」。审核页 `自动审核` Tab 副文案 ⑯ 常驻说明这件事。

### 4.5 人的四种介入动作（后果互不相同，不得混写）

| 动作 | 做什么 | 改 `track` | 改结论 | 入口 | 端点 |
|---|---|---|---|---|---|
| 转人工审核 | `auto → human`，对象自然脱批（不再满足 §4.4） | ✅ | ❌ | 卡片 `⋯` / 抽屉 `⋯` / 审核表单页脚 | 现成 `POST /tasks/:id/review/escalate` |
| 人抢审（接管并审） | **先换轨再写结论**（C6：条件写与 escalate 同一条实现，审计 `reason:'人抢审即接管'`） | ✅ | ✅ | 审核页队列主按钮 / 审核表单提交 | 现成 `POST /tasks/:id/review` |
| 从批次摘出 | 删 `review` 边，仍留在自动轨等别的轮次/批次 | ❌ | ❌ | 依赖 Tab 行内 / DAG 边删除 / 批次抽屉行右 | 现成 `DELETE /tasks/:id/dependencies/:depId` |
| 删除批次 | 批次连同它的边消失 | ❌ | ❌ | 危险操作组 | 现成删除，确认文案 ⑫ |

**没有「人工结案」**：`READY→DONE` 是矩阵 ❌，也不给它开专用端点（§2 第 4 行）。空批的人工出路是现成 ✅「撤回」（READY→BACKLOG），
批次回需求池等复用，或等对象重跑时按 §4.3 另建。

### 4.6 失败、阻塞、租约、归档、删除

- 批次 `fail_task` → `FAILED`（沿用现状，可 ✅「重试」回 READY）；被审对象留在 `REVIEW/track=auto` 不动。
- **租约回收是既有机制，不是本方案新增的定时器**：`lease.service.ts:73,183-215` 的扫描把过期 RUNNING 置 `FAILED`
  （**不是回 READY**），批次照常受它管辖 → 恢复路径永远是 `FAILED → 重试 → READY`。
  P5 禁的是「为审核新增超时/兜底定时器」，不是禁这条既有回收。
- 批次 `block_task` → `BLOCKED`（N22）：Agent 判到一半需要人给信息时的正常出口。批次**不是**被审对象，
  阻塞不影响任何对象的 track；出路沿用 BLOCKED 列现成三条 ✅（重试 / 退回需求池 / 按失败结案），不新增格子。
- 对象在 REVIEW 被归档 → `archived_at` 使 §4.4 判定落空，自然脱批；批次侧不删边。
- **批次被归档 = 等同摘出**（N24）：它的对象失去覆盖，停在 `REVIEW/track=auto`，
  出路只有「重新打包送审」（§5.6，同一批对象可再选）或逐支「转人工审核」；平台不因归档自动换轨。
- 对象/批次被**删除** → `task_dependencies` 的行随 `ON DELETE CASCADE` 消失（`0001_init/migration.sql:39-40`），
  批次覆盖数自然减少，可能变空批（§5.2 的 ④ 出路）。
- 除上述既有租约回收外，平台不重试、不计时、不因「等太久」改任何状态（P5 + 0928 Q3 裁定不动）。

### 4.7 批次收工

「本轮有结论生效」= 阶段二里实际写了 `reviews` 行（APPROVE/REJECT）或换轨成功（ESCALATE）的条数；`skipped[]` 不计。

| 场景 | 批次落点 | 剩余对象 |
|---|---|---|
| 生效 ≥1 条，仍有可审对象 | `RUNNING → READY`（下一轮） | 留在 `REVIEW/track=auto` |
| 生效 ≥1 条，无可审对象（全 DONE / 全转人工 / 全脱批） | `RUNNING → DONE` | — |
| 生效 **0 条**（空回写，或全部 skipped） | `RUNNING → DONE` + **剩余可审对象全部 `track=human`** | 转人工 + 逐支 `review_pending` |
| 有对象预算耗尽（`used ≥ max`） | 按上面三行继续；耗尽的那些在分流时已被 §4.1 挡住不再回自动轨 | `track=human` |

第三行是防「Agent 反复领取又反复不判」的空转回路：生效数为 0 即视为审核器放弃，交给人，**平台不重排、不重试**。

## 10. 验收要点

**回路正确性**

1. 对象 complete 落 `REVIEW/track=auto` 的同事务里出现批次（或挂进已有批次），批次由 `BACKLOG` 即刻 `READY`；断言不存在「批次永远领不到」的路径。
2. 执行者 Token 在池里看不到「唯一对象是自己跑的」批次；换 Token 立即可领；混合批次可领且载荷把 self 对象标出来；
   对象 `current_run_id` 为空或 Run 的 `token_id` 为 NULL 时**不得**判成 self（N29）。
3. 对 self 对象给结论 → `422 SELF_REVIEW_FORBIDDEN` 且**整批不落**；跳过它回写 → 它留下一轮，别的对象照常流转。
4. 批次带 ≥1 条生效 verdict 且仍有可审对象 → 批次 `RUNNING→READY`；非批次给这个落点 → 409。**矩阵快照测试文件不得被改动过一格。**
5. 本轮生效数为 0（空 `items` 或全部 skipped）→ 批次 DONE + 剩余可审对象全部 `track=human` + 逐支 `review_pending`。
6. 对象第 `review_max_rounds` 次 Agent 结论之后再次完成回写 → 直接 `track=human`，**不建不挂批次**（跨批次、跨重跑都不重置预算）。
7. 追加到 RUNNING 批次的对象本轮不被判，批次卡显示 `本轮未覆盖 1 支`；同一对象被两支活跃批次覆盖的尝试 → `409 ALREADY_IN_ACTIVE_BATCH`；
   被驳回 → 重跑 → 再回自动轨的对象**回到同一批次同一批边**，不新建边。
8. 人接管（escalate 或抢审）后：`review_track=human`，抢审场景下 `reviews.reviewer_type='user'` 同批写入，不得出现「DONE ∧ track=auto」。
9. **轮中被抢走**：Agent 领取后人把某支转人工，Agent 再回写该支 → 该支进 `skipped[]`（不 422/409），其余条目照常生效，`applied` 数正确。
10. **两阶段不破事务**：断言批次回写期间不存在嵌套 `$transaction`（阶段一提交后才逐支落地）；阶段二中途某支抛错 → 批次停 RUNNING、评论按 ⑱ 留痕、重领后只判未落定对象。
11. 归档/删除批次后其对象失去覆盖：track 仍 `auto`、停在 REVIEW，出路只有打包或逐支转人工（文案 ⑫ 与 §4.6 一致，不得静默换轨）。
12. `审核` 类型在四个建单面全部 `422 TASK_TYPE_RESERVED`，`get_vocabulary` 的 `task_types` 不含它。

**接口与契约**

13. 批次载荷 `skills` 带判据正文；`review_rubric_skill=''` 时载荷技能为空但回路照常。
14. 批次 complete 缺 `review_verdict` → `422 VERDICT_REQUIRED`；`items[].task_id` 不属于本批次 → `422 VERDICT_TARGET_UNKNOWN`；`items` 无 `run_id` 位。
