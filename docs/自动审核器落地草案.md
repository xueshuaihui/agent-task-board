# 自动审核器落地草案 · 第三版「审核批次任务 + 审核回路」（2026-09-29 讨论稿）

> 状态：**待用户审核**，本版为最新权威版（前两版在 git 历史：`2603bce` 审核即任务、及其前一个专用队列版）。
> 本版依据用户 2026-09-29 三点裁定重写：
> ① **不考虑历史数据**（迁移可干净重做，不写兼容与回填）；
> ② 审核是一个**特殊任务**，它专门审核**一个或多个**任务；
> ③ 审核任务与被审任务之间形成**回路（loop）**，且**可配置上限**。
> 设计公理沿用上版 P1–P5：平台只存储 / 下发 / 回写，**一切工作皆任务**，技能随任务下发，平台不起进程、不设计时器。

---

## 1. 主模型（一句话）

`review_mode=auto` 的任务完成回写后，不再等平台侧的审核队列，而是**由平台派生一支「审核」类型的任务**：
它声明覆盖 N 支被审任务，等到这些任务里**有任意一支进入「待审核」**就被激活进待执行，
被任何**非执行者** Token 经常规认领链路领走、审完回写结论，
平台按结论分别流转各被审任务，并决定这支审核任务**回待执行跑下一轮**还是**落已完成收工**——
轮次与批次容量都是设置键，触顶就整批转人工。

## 3. 数据模型

### 3.1 「审核」任务

一支普通 `tasks` 行，靠三个特征成为特殊任务：

1. `type = '审核'`（`DEFAULT_TASK_TYPES` 追加；类型词表可被用户在设置页删改，所以**判定不靠 type**，见第 2 点的列）；
2. `review_target_flag`：新列（迁移 0021）`tasks.review_batch INTEGER DEFAULT 0`——**1 表示这支任务是审核批次任务**。
   为什么不能只看 `type`：类型是用户可增删的自由词表，把行为钉在自由词表上会让用户删掉「审核」这个词就把回路打断；
3. `review_mode = 'none'`——审核任务自己不进审核，否则无限递归（`none` 在这里的含义是「它的 complete 就是结论落地」）。

### 3.2 覆盖关系：第三种依赖边 `review`

- `task_dependencies` 的 `type` CHECK 扩为 `('blocks','relates','review')`（0001 建表法需整表重建，照 0018 教训保住既有索引）。
- 方向：`审核任务 T-a` 的边指向 `被审任务 T-b`（`task_id = T-a, depends_on = T-b, type='review'`），N 条边 = 审 N 支。
- **不参与**环检测与认领过滤（与 `relates` 同级）：它只是归属声明，激活靠下面 §4 的状态动作，不靠依赖解锁。
  这条是本版与用户原话唯一有出入的地方，理由见 §2 第一行的死锁。
- 反查「这支任务被哪个批次覆盖」：`WHERE depends_on = ? AND type='review'` 一条索引查询。

### 3.3 轮次与批次上限（两个新设置键 + 一列）

| 键 / 列 | 默认 | 含义 |
|---|---|---|
| `tasks.review_batch`（列，0021） | `0` | 标记这是审核批次任务 |
| `review_batch_max_targets`（设置） | `5` | 一支批次最多覆盖几支被审任务（建批与追加时校验） |
| `review_max_rounds`（设置） | `3` | 回路最多跑几轮；比较对象是批次任务的 `run_count` |
| `review_auto_dispatch`（设置） | `true` | `complete` 分流是否自动挂批次（关掉＝只允许人工打包） |

### 3.4 判据（rubric）

做成一条内置默认技能「自动审核判据」（分类 `编码开发 / 质量与安全`，随包发布、`SKILL_READONLY`），
建批次时绑到批次任务的 `skills` 上 → 认领载荷 `AgentTaskPayload.skills` 自动把正文带下去（技能随任务下发，公理 P3）。
新设置键 `review_rubric_skill` 可指向用户自写的技能。

## 4. 生命周期与回路（本版核心）

### 4.1 状态动作序列

```
被审任务 T-b（review_mode=auto）
  complete_task ─┬─→ T-b: RUNNING → REVIEW / review_track=auto
                 └─→ 平台同事务【挂批次】：
                      已有可复用批次？
                        ├─ 是 → 给该批次补一条 review 边（覆盖数 ≤ review_batch_max_targets）
                        └─ 否 → 新建批次 T-a（type=审核, review_batch=1, review_mode=none,
                                      status=BACKLOG, skills=[判据技能], 证据写进 description）
                      若 T-a 处于 BACKLOG → 立刻 BACKLOG → READY（激活）

批次 T-a（READY，在认领池里）
  claim_next_task（任何非执行者 Token；租约/幂等沿用现状）
    认领侧过滤：批次内**全部**被审对象都不在「可审」状态时，跳过该候选（见 4.2）
  → RUNNING，agent 审完
  complete_task（带 review_verdict，见 §6）
    ├─ 平台按 verdict 逐支流转被审任务：APPROVE → DONE；REJECT → READY/BACKLOG；
    │   未给结论的 → 原样停在 REVIEW/track=auto
    ├─ 回路判定：仍有被审对象处于 REVIEW/track=auto（或后续会再回来）
    │      ├─ T-a.run_count < review_max_rounds → T-a: RUNNING → READY（下一轮，run_count 已在认领时 +1）
    │      └─ 触顶 → 剩余对象全部 track=human + 推 review_pending，T-a → DONE，评论记「轮次耗尽转人工」
    └─ 全部对象已落定（DONE 或已被人接管）→ T-a → DONE
```

**「激活」为什么不靠依赖**：被审任务停在 `REVIEW` 不是 `DONE`，`blocks` 边会让批次永远进不了池（§2）。
改用**状态动作**表达用户的原话——「a1、a2 进入待审核状态后 a 就启动激活」＝
被审任务 `complete` 落 REVIEW 那一刻，平台把覆盖它的批次从 BACKLOG 推到 READY。
平台做的是一次**状态流转**（现有流转，`BACKLOG→READY` 是已验收动作），不是判断，完全在 P1 之内。

### 4.2 「可审」判定与认领侧过滤

批次任务对认领池的可见性条件（`CANDIDATE_SELECT` 给 `review_batch=1` 的行加一条 EXISTS）：

- 至少一条 `review` 边指向的任务满足：`status='REVIEW' ∧ review_track='auto' ∧ archived_at IS NULL`；
- 且该对象被审 Run 的执行者 Token ≠ 调用方（自审门禁，换到认领侧：自己干的活不派到自己面前）。

两者都不满足时，批次**不进候选**（不报错、不占坑）——被审任务还没跑完，或全被人接管了。

### 4.3 人接管（「转人工审核」在批次语义下）

单支被审任务点「转人工审核」＝ `review_track=human`（现有实现），它自动不再满足 4.2 的「可审」判定，
于是从批次里**自然脱出**——不删边（历史可追溯）、不需要新端点。
全部对象都被接管时，批次不再可领；人在批次卡片上可「结案」→ `DONE`（评论记未覆盖原因）。

### 4.4 失败与租约

- 批次任务 `fail_task` / 租约过期 → 沿用现状（`FAILED`、可重试），被审任务留在 `REVIEW/track=auto`；
- 平台**不重试、不计时**（0928 Q3 裁定不动）；重试=人点重试或外部调度再领。

## 5. 交互设计（用户点名的重点）

### 5.1 看板卡片

| 位置 | 呈现 | 要点 |
|---|---|---|
| 「待执行」列 · 批次卡 | 类型徽标换成**审核专用符号**（放大镜/天平），标题保留「审核 · N 支 · 第 R/max 轮」；副行显示覆盖对象短号列表（`T-1008 T-1012`） | 轮次分母来自设置键，让人一眼看出「这是第 2/3 轮」，越接近触顶越醒目（第 3 轮起角标变警示色） |
| 「待审核」列 · 被审卡 | 现有两态角标之外，加一行**「由 T-1050 审核（第 2 轮）」**，短号可点跳到批次抽屉 | 人必须能回答「现在谁在审、审到第几轮」，否则自动轨是黑箱 |
| 「需求池」列 · 批次卡 | `status=BACKLOG` 的批次显示「等待审核对象进入待审核」 | 派生即建、但还没激活的批次要看得见，否则用户以为「建了个死任务」 |

**列污染取舍**：批次任务会占用「待执行」列。建议给它一个看板过滤预设（列头筛选里预置「类型≠审核」），
不新增列、不改七列矩阵（状态集合是 0020 非目标）。这条见 Q4。

### 5.2 批次任务详情抽屉

- 概览顶部一块 **「审核对象」区**：覆盖 N 支，每支显示短号、标题、当前状态、`track`、本轮 verdict（若有）、历史结论数；
  行可点开对应被审任务抽屉。
- 「审核」Tab 对批次任务改为**「本批次结论汇总」**（它自己 `review_mode=none`，天然没有自己的审核记录）：
  逐轮列出 `第 1 轮：通过 2 / 驳回 1 / 未判 0`，每条链到被审任务。
- 底部动作条：`READY` 态显示「结案」（全部对象已被接管/落定时）；`BACKLOG` 态显示「确认可执行」（人工提前激活）。

### 5.3 被审任务侧

- 「审核」Tab 每条 Agent 出的结论加一行来源：**「第 2 轮 · 由批次 T-1050 审」**（点跳批次）；
- 「转人工审核」保留现位置（卡片 `⋯` + 审核表单页脚），文案补后果：「该任务从批次 T-1050 脱出，等你审」；
- 「依赖」Tab 里 `review` 边单独分组显示（标题「审核批次」），与 blocks/relates 并列但不混排。

### 5.4 打包送审（人工发起的入口）

REVIEW 列支持多选（沿用现有卡片多选面）→ 工具条按钮「**打包送审**」：
弹窗展示将被覆盖的任务清单、当前批次容量（`n/5`）、判据技能选择器（默认「自动审核判据」），
提交后建批次（`status=READY`，因为此刻对象已在 REVIEW）+ N 条 `review` 边 + 每支一条评论。
`review_mode=human` 的任务在选择器里**置灰并注明**「人工审核的任务不进批次」。

### 5.5 流程图 / DAG

- `review` 边用第三种样式：虚线 + 专属色，tooltip「审核：T-1050 → T-1008（第 2 轮）」，点击可删（删除＝从批次摘出，语义与「转人工」区分开：删边是「不再由它审」，换轨是「改由人审」）；
- 工具栏图例与 `board.view` 设置里加一个开关（默认开）。落点：`DependencyGraphCanvas.tsx:353-378`（现按 `edge.type` 分支渲染）与 `DependencyGraphDialog.tsx:113-114` 的类型下拉。

### 5.6 审核页（人工队列）

- 顶部新增一行只读汇总：「自动轨 **N** 支 · 活跃批次 **M** 个 · 最近一次审核器活动 **T**」
  （T 取 `reviews` 里最新的 `reviewer_type='agent'` 行，零新列零计时器）；
- 「等 Agent 审」的卡片加「第 R/max 轮」小标；触顶批次（R=max）整批高亮，提示「本轮结束后自动转人工」。

### 5.7 设置页（通用页签新增四项）

`review_auto_dispatch` 开关 / `review_batch_max_targets` 数字 / `review_max_rounds` 数字 / `review_rubric_skill` 技能选择。
文案要写清：「审核由 Agent 执行，平台不代为判断；轮次触顶后自动转人工，不设超时」。

### 5.8 通知

不新增 kind（避免词表再膨胀）：批次派生与轮次推进沿用 `review_auto_pending`（消息文案带上批次短号与第几轮），
结论落地沿用 `review_auto_passed`，轮次耗尽/接管沿用 `review_pending`。
通知中心归类不动（自动轨两条仍在「一般通知」）。

## 6. 接口面（MCP / REST）

**删除**：`claim_next_review`、`submit_review` 两个 MCP 工具与 `ReviewQueueService.claimNextReview`

**新增/扩展**：

1. `completeSchema` 加可选块（审核任务的 complete 必带，普通任务带了就 422）：

```ts
review_verdict: {
  items: [{                       // ≤ review_batch_max_targets 条
    task_id: string,
    conclusion: 'APPROVE' | 'REJECT' | 'ESCALATE',
    suggestion?/reason?/detail?,  // REJECT 三者必填，走同一份 reviewSchema 校验
    return_to?: 'READY' | 'BACKLOG',
    priority_adj?: number,
```

   `review_batch: 1`、`review_targets: [{id, title, status, track, run_id, evidence}]`——

   新增 `review_verdict` 与三个设置键的说明；`task_types` 追加「审核」。

## 8. 待拍板（四题）

- **Q1 批次怎么建**：A（推荐）**自动挂批**——`complete` 分流时把对象挂到「同一分组/父任务下最近一个未结案批次」，
  满了或没有就新建；B 只允许 §5.4 的人工打包（全自动变全手填，与 opt-in 初衷相悖）；
  C 两者都要（默认自动，人可随时打包补建）。
  自动挂批的**聚合键**要一起定：按 `group_id`（推荐）/ 按 `parent_task_id` / 全局单批。
- **Q2 批次任务的创建者身份**：`origin_type='agent'` + `origin_agent='review-dispatch'`（推荐，不动 0013 CHECK）
  / 或扩 CHECK 加 `'system'`（更诚实，但多一次表重建）。
- **Q3 触顶后的动作**：A（推荐）剩余对象**整批转人工**（track=human + `review_pending`），批次 DONE；
  B 批次停在 READY 并标「已达轮次上限」，等人手工结案或手工提高上限；
  C 不设上限（无限循环，成本不可控）。
- **Q4 批次卡在看板的默认可见性**：A（推荐）照常混在「待执行」列，提供类型过滤预设；
  B 在「待执行」列内单独分组置顶；C 新增一条独立泳道（0020 已裁：泳道与列结构不动，C 需另开需求）。

## 9. 非目标

- 平台侧起任何进程、任何模型调用、任何出本机的网络请求；平台代拟任何审核结论。
- 用 `blocks` 表达审核依赖（§2 的死锁）；用超时定时器推进回路（0928 Q3 裁定）。
- 批次任务再被审核（递归审核）、审核链多层（A 审 B、B 审 C）。
- 历史数据兼容与回填（本版明确不考虑）。
- 七列状态集合变更。

## 10. 验收要点

1. 被审任务 `complete` 后同事务出现批次（或挂进已有批次），批次由 `BACKLOG` 即刻 `READY`；断言不存在「批次永远领不到」的死锁路径。
2. 执行者 Token 在池里看不到唯一对象是自己跑的那支的批次；换 Token 立即可领。
3. 一轮 `complete(review_verdict)` 后：APPROVE 支 DONE、REJECT 支回 READY/BACKLOG、未判支留 auto；批次按 4.1 判定回 READY 或 DONE，`run_count` 与轮次文案一致。
4. 触顶（`run_count == review_max_rounds`）时剩余对象整批转人工 + 推 `review_pending` + 批次 DONE + 评论留痕。
5. 人点「转人工审核」后该支从批次脱出（4.2 判定不再成立），批次若失去全部对象则不可领、可手工结案。
6. DAG 里 `review` 边渲染为第三种样式，可加可删；删边只脱批、不改 `track`。
7. 批次任务的 `skills` 载荷带判据正文；`review_rubric_skill` 改指用户自写技能后载荷随之变化。
8. 回归须主动查：看板各列（需求池/待执行/执行中/待审核/已完成/异常）在 960px 与 1280px 两档下不因批次卡与新增行溢出；
   `board?requirements` 完成度**不得**把批次任务算进分母；筛选、分组视图、全局搜索、CSV 导出对新类型的处理不崩。
