# 一、背景与目标



## 1\.1 背景



Codex、Qoder、Claude Code、Cursor 等 Agent 客户端已具备定时任务与自动化能力，但缺少一个统一的任务来源与审核入口。用户希望：



1. 有一个看板集中管理任务。

2. Agent 自己能定时来领任务执行，而不是人工逐个派发。

3. 执行结果有统一的地方审核。

4. 审核意见能反馈给 Agent，指导下一次执行。

5. 任务之间有依赖关系，Agent 抓取时遵守依赖顺序。

    

## 1\.2 定位



一个**桌面端**的**任务看板**，作为 Agent 的任务来源与结果审核中心。



交付形态为 **Tauri 桌面应用**，由两部分组成：

- **原生主窗口**：用户操作界面（看板、审核、依赖图、设置），由 Tauri WebView 加载应用内置前端资源，不依赖外部浏览器。

- **常驻本地服务**：`127\.0\.0\.1:7788`，只提供 Agent 侧的 REST / MCP / WebSocket 端点，不再对外提供 Web 页面。



两者由同一次启动拉起，但**主窗口可关闭**（隐藏到托盘），本地服务全程常驻。



## 1\.3 目标



1. 任务看板：任务可视化流转。

2. 任务队列：Agent 可通过 MCP HTTP / REST API 领取任务。

3. 结果回写：Agent 回写进度、日志、产物。

4. 人工审核：每个任务必须人工审核，填写建议、原因、详情。

5. 审核反馈：审核意见保留，Agent 下次可读取。

6. 零 Agent 管理：平台不管理 Agent，只提供接入接口。

7. 常驻服务：Agent 未调用、主窗口未打开时，用户也可从托盘唤起看板配置任务。

8. 桌面应用：Tauri 原生主窗口 \+ 托盘图标，本地运行，不依赖外部浏览器。

9. 自定义字段：支持用户自定义任务字段。

10. 产物预览：支持 diff、图片等内嵌预览。

11. 任务依赖：支持阻塞依赖，Agent 抓取时严格遵守。

12. 任务模板：支持预填字段。

13. 导入导出：支持 JSON / CSV。

14. 批量归档：支持手动与自动归档。

15. 依赖图：支持 DAG 视图。

    

## 1\.4 非目标



1. 不主动触发 Agent。

2. 不管理 Agent 生命周期。

3. 不做多用户与权限。

4. 不做外部任务同步。

5. 不做自动审核。

6. 不做任务强制拆解。

7. 不做代码托管。

8. 不做平台侧并发限制。

9. 不做开机自启。

10. 不做 stdio 模式 MCP。

11. 不做产物全文检索。

12. 不做多语言界面。

13. 不做浏览器访问的 Web UI：`7788` 只提供 Agent 侧 REST / MCP / WS 端点，根路径不返回看板页面，也不提供局域网访问。

# 四、看板与状态机



## 4\.1 看板列



**六列，从左到右固定顺序：**



```Plain Text
需求池 → 待执行 → 执行中 → 待审核 → 已完成 → 异常/失败
```



|列|状态|说明|
|---|---|---|
|需求池|`BACKLOG`|新建任务、驳回回退的任务|
|待执行|`READY`|可被 Agent 领取（含被阻塞任务，显示阻塞角标）|
|执行中|`RUNNING`|Agent 已认领，正在执行；**不可由拖拽产生**|
|待审核|`REVIEW`|Agent 执行完，等待人工审核|
|已完成|`DONE`|审核通过|
|异常/失败|`FAILED`|Agent 上报失败、租约超时、或用户强制停止|



**列显示规则：**



- 六列全部存在，看板横向滚动；「异常/失败」列在最右。**折叠只有一条规则：列内无可渲染卡片时该列折叠为 40px 竖条**（仅列头 \+ 计数），有卡片时自动展开。差别只在默认视图（`view=all`）下其余五列即使为空也保持 280px 占位——空列在默认视图里是"这一类确实没活"的信息，而筛选视图里的空列只是噪声；「异常/失败」列例外，它常驻折叠态是垃圾抽屉，不该长期占 280px。

- 每列头部显示该状态任务总数；列内**最多渲染 50 张卡片**，超出时列底出现「查看全部 →」，跳转「任务列表」页（见 6\.1 第 8 条）。

- 「已完成」列默认按 `updated_at DESC` 排序，其余列按抓取顺序（5\.6）排序。

- 列宽、列头规格见原型 3\.1、3\.2。



## 4\.2 流转图



```Plain Text
需求池 ──► 待执行 ──► 执行中 ──► 待审核 ──► 已完成（终态，不可回退）
  ▲          ▲           │            │
  │          │           │            │ 驳回 / 退回重跑（均填审核意见）
  │          │           │            ▼
  │          │           │        需求池 或 待执行
  │          │           │
  │          │           │ 失败上报 / 租约超时 / 用户强制停止
  │          │           ▼
  │          └──────  异常/失败
  └───────────────────┘  重试
```



`DONE` 为终态：不回退到任何其他状态。需要重做请新建任务并把原任务设为其前置（规则见 4\.3\.1 第 6 条）。



## 4\.3 操作



**用户：**



|操作|转移|前置条件 / 副作用|
|---|---|---|
|确认可执行|需求池 → 待执行|校验标题、类型、优先级、必填自定义字段|
|撤回|待执行 → 需求池|无|
|**强制停止**|执行中 → 异常/失败|二次确认；**吊销租约**（置 `lease_revoked_at`）；`stop_reason = 'user_stop'`|
|审核通过|待审核 → 已完成|审核表单，必填建议、原因、详情|
|驳回|待审核 → 待执行（默认）/ 需求池|审核表单，必填建议、原因、详情；可选调整优先级|
|**退回重跑**|待审核 → 待执行|等价于「驳回」：弹审核表单并预填 结论=驳回、退回目标=待执行，三字段仍必填（可「复用上次意见」一键填充）|
|重试|异常/失败 → 待执行 / 需求池|无|
|置顶 / 取消置顶|不改状态|任意状态可用，影响抓取顺序（5\.6）|
|归档|不改状态，置 `archived_at`|**仅 `DONE`**，且无未完成的前置任务引用它（4\.3\.1 规则 3）|
|恢复|清 `archived_at`|仅已归档任务|
|**删除**|物理删除|4\.3\.1 规则 4；`RUNNING` 需先强制停止|

    

**Agent：**



- 待执行 → 执行中：原子认领（依赖已满足）

- 执行中 → 待审核：完成回写

- 执行中 → 异常/失败：上报失败

    

**系统：**



- 租约超时：执行中 → 异常/失败

- 依赖满足：阻塞任务自动解锁（仍在待执行列）

- 自动归档：已完成超 N 天自动归档

    

## 4\.3\.1 关键规则


- **1. 「执行中」不是拖拽目标。** 该列只能由 Agent 认领产生，也**不能从该列拖出**。用户的唯一干预入口是卡片上的「强制停止」按钮。UI 上拖向/拖出该列时目标列高亮为红色禁止态并 Toast 提示，见 4\.5。

- **2. 强制停止只吊销租约，不下发中止指令。** 平台与 Agent 之间没有下行通道（见 1\.3「零 Agent 管理」边界）：停止后任务立即置 `FAILED`、`stop_reason = 'user_stop'`，Agent 后续的回写会拿到 `410 LEASE_REVOKED`（4\.3\.2）。确认弹窗文案必须写明这一点：「Agent 可能仍在继续执行，平台不再接受它的结果。」

- **3. 归档不能造成依赖死锁。** 归档 `DONE` 任务前校验：若它仍是某条 `blocks` 边的**前置**且下游任务未完成，拒绝归档，返回 `409 ARCHIVE_BLOCKED_BY_DEPENDENCY`。自动归档任务遇到该情况时跳过并在审计日志记一条 `archive_skipped`，不重试到死循环。

- **4. 删除是物理删除并级联。** 删除任务时级联删除 `task_runs`、`reviews`、`artifacts`（含磁盘文件）、`logs`、以其为**任一**端点的 `dependencies`。删除确认文案必须包含：「将同时删除 N 条执行记录及其产物；若解除下游阻塞，下游任务会立即可被领取。」`RUNNING` 任务须先强制停止才可删除。

- **5. 驳回与退回重跑都产生审核记录。** 两者均写入 `reviews`（`conclusion = 'REJECT'`），差异只在退回目标。审核页历史列表不区分二者，避免"退回重跑没留意见"的空档。

- **6. `DONE` 不可逆。** 不提供"已完成 → 待执行"的路径。需要重做时新建任务，并在 `dependencies` 里把原 `DONE` 任务设为其前置（`blocks`），从而保留可追溯的因果链。


## 4\.3\.2 租约与回写语义


`lease_ttl_minutes` 默认 30，可在设置页修改并热生效（仅影响此后新认领的租约）；`heartbeat_interval_seconds` 默认 300。租约由后台每 30 秒扫描一次过期项。

所有 Agent 写回接口（`complete_task` / `fail_task` / `heartbeat` / `update_progress` / `append_log`）统一按入参三元组 `task_id` \+ `run_id` \+ `lease_id` 校验，校验链：


```Plain Text
token 有效 → task 存在 → run 存在且 run.task_id = task_id
          → run.lease_id == 入参 lease_id
          → task.lease_revoked_at IS NULL
          → task.lease_expires_at > now
```

任一环节不满足时的返回：


|场景|租约状态|Agent 调用写回|任务状态|返回|
|---|---|---|---|---|
|正常持有|有效|`complete_task`|`RUNNING`|200，转 `REVIEW`|
|超时被扫描回收|已过期|`complete_task`|`FAILED`|`410 LEASE_EXPIRED`，Agent 须丢弃结果|
|超时**未**被扫描回收|已过期|`complete_task`|`RUNNING`|回收为 `FAILED` 后返回 `410 LEASE_EXPIRED`（同一事务内判定，不出现"过期租约仍可完成"）|
|用户强制停止|已吊销|`complete_task`|`FAILED`|`410 LEASE_REVOKED`|
|任务被删除|随任务消失|`complete_task`|—|`409 TASK_GONE`|
|重复回写（网络重试）|已随完成清空|`complete_task`|`REVIEW`|**200 幂等**：`run_id` 已属该任务且 `status = REVIEW` 时返回当前任务，不报错|
|认领但无可领任务|—|`claim_next_task`|—|**200**，body `{ task: null, reason: "no_ready_task" \| "all_blocked" }`（不用 204，204 不允许带响应体）|

`410` 与 `409` 的语义分工：`410` 一律表示"这个租约已失效，丢弃你的结果"，`409` 表示"任务层面的状态不允许此操作"。失败上报 `fail_task` 在租约失效时同样返回 `410`，但**不覆盖**已被回收的 `FAILED` 状态与原有 `stop_reason`。


## 4\.4 并发说明


- 同一任务在任一时刻只能被一个**有效租约**持有，不可并行执行。"有效"= 未过期且未吊销。

- 该不变量由数据库兜底，不只靠认领 SQL 写对：`task_runs` 上建立部分唯一索引 `UNIQUE (task_id) WHERE status = 'RUNNING'`，同一任务至多存在一条进行中的 Run（DDL 见 11 章）。认领 SQL 见 9\.3，条件更新 \+ 外层二次校验，并发下第二个事务匹配 0 行并返回"无可领任务"，而不是覆盖前者的 `lease_id`。

- 不同任务可被并行执行，无论是否来自同一个 Agent 客户端。

- 平台不限制单个 Agent 客户端同时领取的任务数量。

- 平台不为 Agent 维度设并发上限，也不维护 Agent 侧的并发状态。看板「执行中」列提供按 Token 分组的当前 `RUNNING` 数量（从 `tasks` 实时计算，非独立字段），仅用于排查孤儿租约，不构成限制。


## 4\.5 拖拽矩阵与提示文案


行 = 卡片当前状态，列 = 拖放目标列。`✅` 直接生效，`🔒` 需先弹表单，`❌` 禁止。


|↓源 ＼ 目标→|需求池|待执行|执行中|待审核|已完成|异常/失败|
|---|---|---|---|---|---|---|
|**需求池**|—|✅|❌|❌|❌|❌|
|**待执行**|✅|—|❌|❌|❌|❌|
|**执行中**|❌|❌|—|❌|❌|🔒 强制停止|
|**待审核**|🔒 驳回|🔒 驳回|❌|—|🔒 审核通过|❌|
|**已完成**|❌|❌|❌|❌|—|❌|
|**异常/失败**|✅|✅|❌|❌|❌|—|


- 源 = 目标：不落卡，无提示。
- `🔒` 三类均弹出对应表单（审核表单 / 强制停止确认框），取消则卡片回原位，不发请求。
- 拖到 `❌` 目标：目标列整体红色描边 \+ 禁止光标，松手不改变状态，仅 Toast。
- `待审核` 行内的 `✅ 驳回` 与 `🔒 审核通过` 区别：拖到需求池/待执行默认走驳回表单（结论预填「驳回」，退回目标预填拖放目标列），三字段仍必填，不可跳过。
- 被阻塞的 `READY` 卡片拖到任何目标都允许（拖到需求池即撤回，同时软删除依赖边前的校验照常执行）；阻塞只影响 **Agent 可领取性**，不影响人工流转。

|已完成拖出|「已完成是终态。需要重做请新建任务并设为其后续」|
|归档被依赖阻塞的任务|「该任务仍是 N 个未完成任务的前置，无法归档。请先处理下游」|
|删除确认|「将同时删除 {n} 条执行记录及其产物。{若解除阻塞: '下游 {m} 个任务将立即变为可执行。'}」|
|强制停止确认|「Agent 可能仍在继续执行，平台不再接受它的结果。」|
|租约已失效（Agent 侧）|`410 LEASE_EXPIRED` / `LEASE_REVOKED`，见 4\.3\.2|
|依赖成环|「依赖关系形成环：{任务标题链}，已取消保存」|

# 五、任务依赖与抓取顺序



## 5\.1 依赖类型



只保留两种：



|类型|语义|对抓取的影响|
|---|---|---|
|`blocks`（阻塞）|A 完成前，B 不可执行|硬性：Agent 不能领取 B|
|`relates`（关联）|仅表示相关，无执行约束|仅展示，不影响抓取|



## 5\.2 依赖方向



一个任务可以有多个前置任务（AND 关系）：



```Plain Text
T-1001 ──┐
T-1002 ──┼──► T-1005（三个都完成，才能领取 T-1005）
T-1003 ──┘
```



- 全部前置任务为 `DONE` 时，T\-1005 才可被领取。

- 不做 OR 关系，避免歧义。

    

## 5\.3 阻塞任务的展示



依赖未满足的任务**仍在「待执行」列**，但显示阻塞标记。



**卡片表现：**



```Plain Text
┌──────────────────┐
│ T-1005           │
│ 集成支付网关      │
│ [需求][P1]       │
│ 🔒 依赖 2 个未完成 │
└──────────────────┘
```



**筛选器：**



- 「可领取」：只看未被阻塞的任务。

- 「已阻塞」：只看被阻塞的任务。

- 默认显示全部。

    

## 5\.4 Agent 抓取时的过滤逻辑



`claim_next_task` 与 `list_ready_tasks` 的查询条件中，增加：



```SQL
AND NOT EXISTS (
  SELECT 1 FROM task_dependencies d
  JOIN tasks dep ON dep.id = d.depends_on
  WHERE d.task_id = t.id
    AND d.type = 'blocks'
    AND dep.status != 'DONE'
)
```



**含义：** 该任务的所有 `blocks` 类型前置任务都已 `DONE`，才能被领取。



**Agent 无需感知依赖。** 平台侧已经过滤，Agent 领到的任务一定是可执行的。



## 5\.5 依赖解锁与通知



- 当某个任务变为 `DONE` 时，平台检查所有以它为前置的任务。

- 若某个任务的所有阻塞依赖都已满足，标记为「已解锁」。

- 看板上该任务的阻塞角标消失。

- 触发 `task.unblocked` WebSocket 事件。

    

## 5\.6 抓取顺序控制



|机制|说明|
|---|---|
|**置顶**（pinned）|用户可置顶任务，临时插队，优先于优先级|
|**优先级**（priority）|数字越小越优先，0 = P0|
|**创建时间**（created\_at）|同优先级下，先创建先领取|
|**依赖**（blocks）|硬性前置约束|



**默认排序：**



```SQL
ORDER BY pinned DESC, priority ASC, created_at ASC
```



**说明：**



- `pinned` 是任务级布尔字段，用户在卡片上可一键置顶。

- 置顶任务是临时需求，优先于优先级。

- 若置顶任务仍有未满足的依赖，仍不可领取。

    

## 5\.7 循环依赖检测



- 添加依赖时，平台检查是否形成环。

- 若 A → B → C → A，拒绝添加并提示。

- 使用递归查询或应用层 DFS 检测。

**任务详情 → 依赖标签页：**

- 不会自动执行。

- 用户可在前置任务上重新处理，或调整依赖关系。

- 不做「级联取消」。

# 六、功能需求



## 6\.1 任务管理



1. 创建任务：标题、描述、类型、优先级、标签、所需能力、自定义字段、截止时间、依赖。

2. 编辑任务：描述支持 Markdown 渲染（`react-markdown`）。

   本期**不做**任务附件与检查清单：全文没有对应界面与验收项，且 `artifacts.run_id NOT NULL`——文件类内容只能由 Agent 在一次 Run 内产生并作为产物入库（20\.6）。用户侧上传文件需要新表与新交互，属于 19\.1 的增强项。

3. 批量操作：批量移动、打标签、归档。

4. 搜索筛选：状态、类型、优先级、标签、自定义字段、依赖状态、时间。

5. 任务详情：六个标签——概览、执行（含按 Run 归组的产物与日志）、审核、依赖、评论、审计；分区与理由见原型 4\.3、4\.5。

6. 置顶：任意状态可置顶。

7. 归档：手动与自动。

8. **任务列表页**（顶部导航「任务」）：表格视图，列为 ID、标题、类型、优先级、状态、标签、Agent、时长、更新时间、操作；复用第 4 条的全部筛选条件与 `GET /api/v1/tasks` 的分页（13 章）。它是**唯一**的表格实现：看板「查看全部 →」（4\.1）与已归档列表（6\.13）都跳到这里并带上对应筛选，看板工具栏**不再另设「列表」视图切换**。

    

## 6\.2 看板



1. 列：需求池、待执行、执行中、待审核、已完成、异常/失败。

2. 卡片：ID、标题、类型、优先级、标签、Agent 名、时长、租约倒计时、异常角标、阻塞角标、置顶标记、可选自定义字段。

3. 拖拽流转，非法拖拽提示原因。

4. 实时更新（主窗口直连 `ws://127.0.0.1:7788/ws`，见 9\.4\.2）。

5. 筛选视图（`GET /board?view=`）：**全部**、**待我审核**（`REVIEW`）、**异常**（`FAILED`）、**可领取**（`READY` 且无未完成 `blocks` 前置）、**已阻塞**（`READY` 且有未完成 `blocks` 前置）。视图是**服务端卡片过滤条件**，不改变六列结构与列顺序；某列在该视图下没有卡片时折叠为 40px 竖条（与「异常/失败」列的折叠规则同一条，见 4\.1），列头计数为该视图下的匹配数。非「全部」视图下工具栏显示当前视图名 \+ 「清除」，避免用户对着五根空竖条找不到北。

6. 依赖图入口：**阶段二**（17\.2）。阶段一入口不出现在顶部导航与看板工具栏，阻塞关系由卡片角标 \+ 详情抽屉「依赖」标签页（6\.5）表达。

    

## 6\.3 任务领取



1. Agent 通过 MCP HTTP / REST API 领取。

2. 原子认领 \+ 租约，防止重复。

3. 支持按能力、类型、优先级筛选。

4. 自动过滤未满足阻塞依赖的任务。

5. 无任务时返回空。

    

**并行领取：**



平台不限制单个 Agent 客户端同时领取的任务数量。Agent 客户端可根据自身并发能力，多次调用 `claim_next_task` 并行领取多个任务。每次调用独立返回一个任务和一个 lease。



## 6\.4 执行回写



1. 进度更新。

2. 日志追加。

3. 完成回写：摘要、产物、状态。

4. 失败上报：错误码、消息、是否可重试。

5. 租约续期（心跳）。

    

## 6\.5 审核



1. 待审核列表。

2. 审核详情：任务信息、执行摘要、diff、测试结果、日志、产物、历史 Run、审核意见。

3. 审核操作：

    - **通过**：必填审核建议、原因、详情 → 已完成。

    - **驳回**：必填审核建议、原因、详情，选择退回目标（默认待执行），可选调整优先级。

    - **退回重跑**与从「待审核」列拖拽到需求池／待执行，走的是同一张表单与同一套校验（4\.3、4\.5），不另设轻量入口，否则三字段必填会被绕过。

4. 三字段必填的口径：去首尾空白后非空即可，无最短字数；单字段 ≤ 2000 字，超出前端截断提示。必填是产品底线（每个任务都要人工留痕），本期不做"一键通过"。

5. **降低重复成本的本期做法**：`review_reuse_last_opinion`（默认开，20\.9）在打开表单时预填该任务**上一次**审核的三字段并聚焦「建议」；`⌘/Ctrl + Enter` 提交；表单草稿按任务存内存，切走再回来不丢。不做模板库、不做批量通过。

6. 审核意见保留在任务上，Agent 下次可读取（6\.6）。审核记录只增不改不删，改判 = 再提交一条，历史按时间倒序全部可见。

    

## 6\.6 审核反馈给 Agent



Agent 下次领取该任务时，`get_task` / `get_review_feedback` 返回最近审核意见：



```JSON
{
  "review_feedback": [
    {
      "run_id": "R-2000",
      "conclusion": "REJECT",
      "suggestion": "签名校验需覆盖空值",
      "reason": "边界场景未处理",
      "detail": "请补充 null 和空字符串测试"
    }
  ]
}
```



## 6\.7 通知



事件：任务进入待审核、执行失败、租约超时、审核驳回、依赖解锁（对应 `notifications.kind`，见 20\.2）。

渠道与形态：


- **站内（阶段一）**：顶栏铃铛角标显示未读数，点击直接跳「待审核」筛选视图。**通知面板**（列表、逐条已读、30 天清理）列阶段二（17\.2），阶段一不落 UI，但 `notifications` 表结构一次到位、照常写入。
- **托盘角标**：在托盘图标上叠加未读数（`>99` 显示 `99+`），窗口隐藏到托盘时是唯一可见的提醒通道。主窗口在前台时托盘角标仍更新，但不弹提示。
- **不做**：macOS / Windows 系统通知中心的推送、声音、第三方 IM / Webhook（19\.1 第 4 项）。

**为什么托盘角标属于本期**：应用定位是常驻后台、窗口可关（9\.4），而「待审核」是流程的人工卡点——不提醒就没人审核，被 `blocks` 的下游会无限期停在待执行。窗口已关闭时站内角标不可见，闭环断在这里。实现上托盘图标与文本已存在（10\.4），只多一次 `set_badge_count` / `overlay_icon` 调用。

落库与保留：写入 `notifications`（11 章），`read_at` 为空即未读；已读通知保留 30 天后清理，未读不删。同一任务同一 `kind` 已有未读时不重复插入，改为更新 `created_at`。



## 6\.8 审计



记录：任务创建、状态变更（含人工流转与**强制停止**）、**租约超时回收**（系统把 `RUNNING` 判为 `FAILED`）、认领、回写、审核、Token 使用、字段定义变更、模板变更、依赖变更、导入导出、备份、归档与跳过归档。动作取值见 20\.2 的 `audit_logs.action` 枚举，界面不自行造名。

## 6\.10 产物预览



### 6\.10\.1 支持的类型



|类型|预览方式|阶段|
|---|---|---|
|`diff`|diff viewer，高亮增删行|一|
|`image`|图片内嵌显示，支持缩放|一|
|`text` / `log`|文本查看器，支持搜索、折叠|一|
|`link`|显示链接，点击外部打开|一|
|`file`（其他）|显示文件信息 \+ 下载按钮|一|

## 6\.12 导入 / 导出



### 6\.12\.1 导出



- 格式：JSON（完整迁移）、CSV（仅任务清单，人读用）。

- 范围：全部任务 / 当前筛选结果 / 选中任务；已归档任务默认不含，可勾选包含。

- **JSON 内容**：任务字段、自定义字段值、依赖关系、标签、置顶状态、`archived_at`，**外加 `custom_field_defs` 与 `task_templates`**。不带字段定义时，换机后 `custom_fields` 的键无处校验（20\.10 会直接 `422`），因此这三者必须一起导出；导出时按"任务 → 字段定义 → 模板"顺序生成，导入时反序先建定义。

- **JSON 不含**：产物文件与日志（20\.6、20\.8）、`audit_logs`（审计不跨机）、`api_tokens`（Token 是机器本地的，导入后需重新生成）、`task_runs` 的 `output`/`error` 正文（保留 Run 的状态与时长用于历史展示，正文超过 64 KB 截断）。

- 产物在导出包里以 `artifacts_missing: true` 标记，UI 提示「产物文件不随导出迁移」。


```JSON
{
  "version": 2,
  "app_version": "0.1.0",
  "exported_at": "2026-09-11T15:00:00Z",
  "custom_field_defs": [
    {"key": "severity", "label": "严重度", "type": "select", "options": ["高", "中", "低"], "required": 1}
  ],
  "templates": [],
  "tasks": [
    {
      "id": "T-1001",
      "title": "...",
      "type": "缺陷",
      "status": "BACKLOG",
      "custom_fields": {"severity": "高"},
      "dependencies": [
        {"depends_on": "T-1000", "type": "blocks"}
      ]
    }
  ]
}
```

`version` 是导出格式版本（整数，本期为 `2`）：导入时 `version` 大于当前支持值直接拒绝并提示升级应用，不做向前猜测。

**CSV**：UTF‑8 **带 BOM**（否则 Excel 打开中文乱码），字段用 `"` 包裹、`""` 转义，行分隔 `\r\n`；列固定为 `id,title,type,priority,status,tags,duedate,dependencies,` \+ 每个自定义字段 `key` 一列。CSV 不含字段定义与模板，因此 **CSV 导入要求目标实例已有同名 `key` 的字段定义**，否则该列整体丢弃并在预览里告警。



### 6\.12\.2 导入



- 格式：JSON（推荐，含字段定义与模板）、CSV（仅任务，需已有字段定义）。

- **导入前自动备份**：执行导入即先触发一次手动备份（9\.3），并在结果页给出该备份文件路径。导入是不可逆的批量写入，没有这一步一旦 `overwrite` 选错就没有退路。

- **ID 冲突策略**（本地已存在同 `id` 的任务时，导入前预览按冲突数强制选择，无默认）：


|策略|行为|限制|
|---|---|---|
|`skip`|跳过冲突任务，只导入不存在的|其依赖若指向被跳过者，按下一条规则处理|
|`overwrite`|按 ID 覆盖本地任务的字段|本地该任务处于 `RUNNING` 时**拒绝覆盖**并计入 `skipped[]`；不删本地 Run 历史，导入的 Run 以 `run_number` 追加|
|`reassign`|丢弃文件里的 `T-`/`R-` 号，按 20\.1 重新分配|适用于"把另一台机器整库搬过来"；冲突为零时不重编号|


- **依赖引用改写**：无论哪种策略，最终落库的 `dependencies.depends_on` 一律指向**导入后真实存在**的任务 ID；指向不存在（或被跳过）任务的依赖边丢弃，并在结果页列出被丢弃的边。

- **状态归一**：导入的 `RUNNING` 一律降为 `READY` 并清空 `lease_id` / `current_run_id`；对应 `task_runs.status` 置 `ABANDONED`（20\.2）。不这样处理就会造出一个"看板显示执行中、但没有任何 Agent 持有租约"的死任务——租约回收定时器也救不回来，因为它是导入进来的、无过期时间可比的租约。`REVIEW` / `DONE` / `FAILED` / `BACKLOG` / `READY` 原样恢复。

- **导入顺序**：字段定义 → 模板 → 任务 → 依赖边 → Run 与审核记录。前置校验失败的单条任务计入 `failed[]` 并继续，不整体回滚（与批量归档一致的逐条语义，13 章）。

- **结果页**：`imported[] / skipped[] / failed[] / dropped_dependencies[]`，四类各自给原因（取 13 章错误码），CSV 的编码、列缺失、类型不符均在此处报，不弹多个 toast。

- **本期边界**：导入的"完整恢复"只在**空实例或全新增**场景下作为验收口径（18 章 26）。往已有数据的实例里做 `overwrite`，本期只保证不崩、不产生悬空引用，不保证历史合并语义。

    

## 6\.13 批量归档



### 6\.13\.1 功能



- 仅 `DONE` 可归档（4\.3 操作表）；其余状态调归档接口返回 `409 TASK_RUNNING`／`ILLEGAL_TRANSITION`。

- **归档不解除下游阻塞**：归档不改 `status`，因此被归档的 `DONE` 任务作为 `blocks` 前置时仍算"已满足"（9\.3 认领 SQL 判的是 `dep.status != 'DONE'`）。

- 反过来，仍是未完成任务前置的 `DONE` 任务**不允许归档**（4\.3\.1 规则 3）：手动归档报 `409 ARCHIVE_BLOCKED_BY_DEPENDENCY`，自动归档跳过并写 `archive_skipped` 审计。不加这条就会出现"前置被归档 → 下游永久阻塞且在看板不可见"的死锁。

- 归档后不出现在看板默认视图，可在任务列表页把 `archived` 切到 `true` 查看（6\.1 第 8 条 / 原型 3\.8；设置页「数据」Tab 的入口跳该页）；`GET /api/v1/board` 不含归档任务（20\.7）。

- 归档任务不参与任何抓取（认领 SQL 已带 `archived_at IS NULL`，9\.3）。

- 归档**不删除**产物与执行记录，只是从看板隐去；彻底移除是删除操作（4\.3\.1 规则 4），两者在卡片菜单里分列且文案不同。

    

### 6\.13\.2 自动归档



- 设置中配置「已完成超过 N 天自动归档」。

- N 默认 30 天，可配置。

- 后台任务每天检查一次。

    

### 6\.13\.3 交互



- 看板选择多个任务 → 右键 → 「归档」。

- 归档任务可在「任务 → 已归档」中查看、恢复。

# 七、交互设计



## 7\.1 信息架构



顶部导航：看板、审核、任务、设置；**依赖图**为阶段二加入（17\.2），阶段一不显示该入口。「任务」即任务列表页（6\.1 第 8 条），看板每列的「查看全部 →」带着状态筛选跳到这里。



## 7\.2 看板交互



- 单击卡片：打开详情抽屉。

- 拖拽：移动到目标列，合法/禁止以 **4\.5 拖拽矩阵**为唯一依据（不在前端另写一套规则）。

- 悬停：快捷操作（编辑、置顶、评论、强制停止、查看执行）。

- 角标：待审核数量、失败数量、租约倒计时、阻塞标记、置顶标记。

    

**拖拽实现约定：**


- 目标列的可放置态在拖拽开始时按卡片当前 `status` 一次性算出：`✅` 正常高亮、`🔒` 显示表单图标、`❌` 红色描边 \+ 禁止光标。
- **乐观更新**：请求成功后再移动卡片；失败（含 13 章 `ILLEGAL_TRANSITION` / `ARCHIVE_BLOCKED_BY_DEPENDENCY`）则回弹到原位并 Toast 对应文案（4\.5 文案表）。不做"先动后回滚"，否则与 WS 推送互相覆盖。
- 同一任务的并发流转以服务端为准：若 WS 先于本地请求返回 `task.moved`，以事件里的 `to` 收敛卡片位置。
- 键盘可达：卡片聚焦后 `←`/`→` 在合法目标列间移动，`Space` 打开详情，`⌘/Ctrl + P` 置顶——与拖拽共用同一个转移判定函数。



## 7\.3 实时更新



- Agent 领取后，卡片从待执行移到执行中。

- 执行中显示进度条、日志摘要、租约倒计时。

- 完成后自动移到待审核，看板角标提示。

- 依赖解锁时，阻塞角标消失。

    

## 7\.4 服务与界面关系



**两个进程，一个应用：**



- Tauri 主程序：原生主窗口 \+ 托盘，启动时拉起 Node sidecar，退出时结束 sidecar。

- Node sidecar：SQLite、REST、MCP、WebSocket，监听 `127\.0\.0\.1:7788`，只服务 Agent 与主窗口内的前端。



**窗口与服务的关系：**



- 关闭主窗口 **不等于** 退出应用：窗口隐藏到托盘，sidecar 继续运行，Agent 仍可领取与回写任务。

- 唤起界面：托盘菜单「打开看板」显示并聚焦主窗口。

- 托盘图标常显运行状态（\+ 端口），sidecar 异常退出时图标转为错误态。

- Agent 未接入时，用户可正常创建、拖拽、审核、配置任务：UI 只依赖本应用，不依赖外部浏览器。



**调用链路：** 见 9\.4。

## 9\.3 关键设计



**任务认领并发控制（SQLite）：**



```SQL
BEGIN IMMEDIATE;                       -- 必须显式发起，见下方实现约束

-- :lease_id / :run_id 由应用层生成 UUID，两处引用同一份值
UPDATE tasks
SET status           = 'RUNNING',
    current_run_id   = :run_id,
    lease_id         = :lease_id,
    lease_expires_at = datetime('now', :ttl),          -- '+{settings.lease_ttl_minutes} minutes'
    claimed_at       = datetime('now'),
    updated_at       = datetime('now')
WHERE id = (
        SELECT id FROM tasks
        WHERE status = 'READY'
          AND archived_at IS NULL
          AND (lease_id IS NULL OR lease_expires_at <= datetime('now'))
          AND NOT EXISTS (
            SELECT 1 FROM task_dependencies d
            JOIN tasks dep ON dep.id = d.depends_on
            WHERE d.task_id = tasks.id
              AND d.type = 'blocks'
              AND dep.status != 'DONE'
          )
        ORDER BY pinned DESC, priority ASC, created_at ASC
        LIMIT 1
      )
  -- ↓ 关键：外层必须重复同一组可领取条件，否则并发下会覆盖他人租约
  AND status = 'READY'
  AND (lease_id IS NULL OR lease_expires_at <= datetime('now'))
RETURNING id, current_run_id, lease_id, lease_expires_at;

-- 上一句 changes() = 0 → ROLLBACK，返回 200 { task: null, reason }（未抢到，不改任何行）
-- 上一句返回 1 行 → 用 RETURNING 的 id / lease_id 建立 Run：
INSERT INTO task_runs (id, task_id, token_id, run_number, status, lease_id, started_at)
VALUES (:run_id, :task_id, :token_id,
        (SELECT run_count FROM tasks WHERE id = :task_id) + 1,
        'RUNNING', :lease_id, datetime('now'));

UPDATE tasks SET run_count = run_count + 1 WHERE id = :task_id;

COMMIT;
```

`ttl`、`lease_id`、`run_id` 均在事务开始前由应用层确定，事务内不再重新生成，保证 `tasks.lease_id` 与 `task_runs.lease_id` 始终同值——回写校验链（4\.3\.2）依赖这一点。



**能力匹配放在哪一步：** SQLite 里没有 JSON 数组的子集运算符，`required_capabilities ⊆ effective`（20\.5）不写进上面的 SQL，而是放在同一事务的候选选取里：



1. `BEGIN IMMEDIATE` 后，先用上面 `SELECT` 的条件取**前 50 条候选**（`ORDER BY pinned DESC, priority ASC, created_at ASC LIMIT 50`）；

2. 在 Node 侧按顺序找第一条 `required_capabilities` 为空或 ⊆ `effective` 的任务，把它作为 `:task_id`；

3. 对该 id 执行外层 UPDATE，`WHERE` 仍带 `status = 'READY' AND (lease_id IS NULL OR lease_expires_at <= datetime('now'))` 的复检；`changes() = 0`（理论上不会发生，因为写锁已在本事务持有）则回到第 2 步取下一条；

4. 50 条全不匹配 → `ROLLBACK`，返回 `{ task: null, reason: 'all_blocked' }`（20\.5 不区分"被阻塞"与"能力不匹配"）。



`BEGIN IMMEDIATE` 已经把写者串行化，所以"选候选"与"占位"之间不会有第二个 Agent 插进来；50 这个数与 `board_column_limit` 无关，只是防止把整张待执行表读进内存，超出部分留给下一次轮询。

**实现约束：**


- `BEGIN IMMEDIATE` 只能串行化写事务，**不能替代**外层条件校验。SQLite 在 deferred 事务下会在 SELECT 后才申请写锁，此时 SELECT 结果可能已失效；Prisma 的 `$transaction` 默认发起 deferred 事务且不暴露 `IMMEDIATE`，因此认领必须走 `$executeRaw` 显式发起事务，或整体收敛到一个原生的 prepared statement。
- 数据库兜底：`CREATE UNIQUE INDEX uniq_active_run ON task_runs (task_id) WHERE status = 'RUNNING';`（11 章）。即使租约字段被错误覆盖，同一任务也无法插入第二条进行中的 Run，异常会以约束冲突暴露而非静默变成孤儿租约。
- 部分唯一索引 SQLite 3.8\+ 支持，Prisma 无对应 schema 语法，需在迁移 SQL 中手写。
- 单实例桌面场景下真正的并发来源只有多个 Agent 客户端同时轮询，SQL 层必须自己扛，不依赖上层排队。



**循环依赖检测：** 添加依赖时，从 `depends_on` 出发做 DFS，若能回到 `task_id` 则拒绝。



**依赖解锁：** 任务变 DONE 后，扫描所有以它为前置的任务，若全部阻塞依赖满足，发送 `task.unblocked` 事件。



**租约续期与过期回收：** Agent 每 `heartbeat_interval_seconds`（默认 300）调用一次 `heartbeat`，把 `lease_expires_at` 推后 `lease_ttl_minutes`（默认 30）。后台每 30 秒扫描 `status = 'RUNNING' AND lease_expires_at <= now`，在**同一事务**内：任务置 `FAILED`、`stop_reason = 'lease_expired'`，清空 `lease_id` / `current_run_id`，对应 Run 置 `FAILED` 并写 `error = 'lease expired'`、`finished_at`。过期后 Agent 仍可能带着旧 `lease_id` 回写，一律按 4\.3\.2 返回 `410 LEASE_EXPIRED`；若此时任务已是 `REVIEW`（说明是重复回写），返回 200 幂等成功。

**孤儿回写：** 若回写的 `lease_id` 匹配得上、但任务已被用户手工移走（状态已非 `RUNNING`），Run 置 `ABANDONED`，产物与日志仍落库并在任务详情「执行记录」里可见，任务状态不回滚——人的操作优先。


**自动归档：** 每天检查一次，将 `DONE` 且 `updated_at` 超过 `auto_archive_days`（默认 30）的任务批量置 `archived_at`。逐条判断 4\.3\.1 规则 3 的前置引用，命中则跳过并写一条 `archive_skipped` 审计，不重试。



**日志轮转：** winston\-daily\-rotate\-file 按大小（单文件 20 MB）和天数（保留 `log_retention_days`，默认 14）双条件轮转，级别由 `log_level`（默认 `info`）控制，目录 `~/Library/Logs/AgentTaskBoard/`（Windows：`%APPDATA%\AgentTaskBoard\logs`）。


**备份与恢复：** 备份只覆盖 SQLite，**不含产物目录**——这是产物在恢复后统一显示「产物文件已丢失（不在备份范围内）」的原因（见 6\.10\.2）。


|项|约定|
|---|---|
|触发|手动：设置页「立即备份」（阶段一唯一切口）；自动：每天 `backup_time`（默认 03:00）——**阶段二**（17\.2），阶段一定时器不注册|
|方式|`VACUUM INTO 'atb-YYYYMMDD-HHmmss.db'`（文件名用本地时间），生成后校验文件大小 \> 0|
|执行期并发|`VACUUM INTO` 是只读一致性快照，**不停写**、不阻塞 Agent 回写；备份目录与数据目录同盘|
|存放|`<数据目录>/backups/`。按 `backup_keep`（默认 7）份自动清理属**阶段二**：阶段一不删任何历史备份，因此设置页备份列表要显示总占用大小，磁盘占用由用户自己负责|
|恢复前置|二次确认，文案写明「当前全部任务、执行记录、审核记录与审计日志将被覆盖，不可撤销；产物文件不在备份范围内，恢复后缺失的产物显示『产物文件已丢失』；当前执行中的任务会全部转为异常/失败。」|
|恢复过程|先对当前库做一次安全备份 → 关闭 sidecar 的写连接 → 用选中文件替换 → 重新迁移建表 → 拉起服务|
|恢复后状态|所有 `RUNNING` 任务置 `FAILED`、`stop_reason = 'lease_expired'`、清空租约（快照时刻的租约在恢复后必然已失效）；WS 全量重连，看板重新拉取|
|恢复失败|替换前失败 → 原库不动；替换后启动失败 → 自动回滚到安全备份并在日志中输出两条路径|
|导入导出的关系|导出为 JSON（6\.12\.1），与备份文件是两种产物：备份用于同机灾难恢复（含审计），导出用于跨机迁移（ID 冲突策略见 6\.12\.2）|



## 9\.4 UI 载体与调用链路



### 9\.4\.1 启动时序



1. 双击应用图标 → Tauri 主进程获取**单实例锁**；已有实例则显示并聚焦其主窗口后退出。

2. 主进程生成一次性 **UI 会话 Token**（随机 32 字节，仅存内存，不落盘）。

3. 主进程以子进程方式拉起 sidecar，通过环境变量注入 `ATB_PORT` 与 `ATB_UI_TOKEN`。

4. sidecar 监听 `127\.0\.0\.1:{ATB_PORT}`，就绪后向 stdout 打印端口回显，主进程据此确认成功。

5. 主进程创建主窗口，加载内置前端资源；WebView 用 `ATB_UI_TOKEN` 发起首次数据请求。



**退出：** 只有托盘菜单「退出」会结束 sidecar 并退出应用；关闭主窗口仅隐藏窗口。



### 9\.4\.2 三条通道



|通道|地址 / 机制|调用方|鉴权|用途|
|---|---|---|---|---|
|REST|`http://127\.0\.0\.1:7788/api/v1/\.\.\.`|主窗口（用户操作）|`Authorization: Bearer <ATB_UI_TOKEN>`|看板、任务 CRUD、审核、设置、导入导出|
|REST|同上|Agent 客户端|`Authorization: Bearer <agent-token>`|领取、回写、心跳（13 章「任务接口」）|
|WebSocket|`ws://127\.0\.0\.1:7788/ws`|主窗口|握手时校验 UI 会话 Token|实时推送|
|MCP|`http://127\.0\.0\.1:7788/mcp`|Agent 客户端|`Authorization: Bearer <agent-token>`|9 个工具|
|Tauri IPC|`invoke` \+ 事件|主窗口 ↔ 主进程|应用内部，无|窗口显隐、托盘、打开日志目录、选择备份路径、文件保存对话框|



**边界原则：** 数据操作一律走 REST（契约只有一份，不为 UI 另写 Rust 层）；只有操作系统与窗口能力走 IPC。



### 9\.4\.3 跨源与 CORS（实现约束）



WebView 的页面源是 `tauri://localhost`（macOS / Linux）或 `http://tauri.localhost`（Windows），访问 `http://127\.0\.0\.1:7788` 属于跨源请求。因此：



- sidecar 必须返回 `Access-Control-Allow-Origin`，取值**精确匹配**上述两个源之一，并允许 `Authorization` 头；

- **不回显任意 Origin**，不接受 `Origin: null`，不接受 `http://127.0.0.1:*`；

- 由此，本机其他进程即使能连上端口，浏览器里的网页也读不到响应内容（详见 15 章）。

- 备选：改用 `@tauri-apps/plugin-http` 在 Rust 侧发请求以绕过 CORS——本期不采用，避免前端代码分叉。



### 9\.4\.4 端口面收敛



- 根路径 `http://127\.0\.0\.1:7788/` 返回 `404`，**不注册任何静态资源中间件**。

- 仅 `/api/v1/*`、`/mcp`、`/ws` 三个前缀可用。

- 不监听 `0\.0\.0\.0`，不提供局域网访问。

看板 UI 由 Tauri 主窗口承载，**不经过此端口**。`7788` 只提供 Agent 与主窗口数据层需要的端点：

|MCP \(HTTP\)|`http://127.0.0.1:7788/mcp`|Agent 用|9 个工具，见 12 章|
|WebSocket|`ws://127.0.0.1:7788/ws`|主窗口用|实时推送，事件表见 13 章|
|~~Web UI~~|`http://127.0.0.1:7788/`|—|**已移除**：根路径返回 404，不再服务页面|

## 10\.2 MCP 传输模式



**仅使用 HTTP 模式，不使用 stdio。**

- 服务独立于 Agent 运行，Agent 不在线时，主窗口内的看板、审核、设置功能照常可用。

## 10\.3 服务生命周期



**启动：**



- 用户双击桌面应用图标。

- 获取单实例锁；若已有实例，显示并聚焦其主窗口后退出（见 9\.4\.1）。

- 拉起 Node sidecar，常驻监听 `7788`。

- 托盘图标出现，主窗口显示看板。



**常驻：**



- 独立于 Agent 运行：Agent 随时可通过 MCP / REST 连接领取任务。

- 独立于主窗口：关闭主窗口只隐藏界面，sidecar 继续运行；用户随时从托盘唤起窗口配置任务、查看状态、审核。



**停止：**



- 托盘菜单 → 退出：结束 sidecar 进程后退出应用。

- sidecar 异常退出：托盘图标转错误态，提示重启（重试点 = 重新拉起 sidecar）。

- 退出时若仍有 `RUNNING` 任务，提示「有 N 个任务正在执行，租约将在超时后回到异常列」，不强制等待。



**端口占用处理：**



- 若被占用，托盘提示并给出选项：换端口启动或终止占用进程。

- 端口写入 `~/.agent-board/config.json`。

- 启动阶段（主窗口尚未创建）失败时，用原生对话框提示，不静默退出。

    

**开机自启：** 本期不做。

# 十一、数据库 DDL（SQLite）



> 所有枚举列的 `CHECK` 取值、默认值与展示名的**唯一来源是 20 章数据契约总表**；改 DDL 必须同步改 20 章，反之亦然。时间列格式与 ID 规则见 20\.1、20\.4。


```SQL
-- 任务
CREATE TABLE tasks (
  id                    TEXT PRIMARY KEY,
  type                  TEXT NOT NULL DEFAULT '需求',   -- 开放词表，见 20.3
  title                 TEXT NOT NULL,
  description           TEXT,
  status                TEXT NOT NULL DEFAULT 'BACKLOG'
                          CHECK (status IN ('BACKLOG','READY','RUNNING','REVIEW','DONE','FAILED')),
  priority              INTEGER NOT NULL DEFAULT 3 CHECK (priority BETWEEN 0 AND 3),
  tags                  TEXT DEFAULT '[]',
  required_capabilities TEXT DEFAULT '[]',
  custom_fields         TEXT DEFAULT '{}',
  pinned                INTEGER NOT NULL DEFAULT 0,
  due_at                TEXT,
  archived_at           TEXT,
  lease_id              TEXT,
  lease_expires_at      TEXT,
  lease_revoked_at      TEXT,                     -- 强制停止时置值，不清空 lease_id
  stop_reason           TEXT
                          CHECK (stop_reason IN ('user_stop','lease_expired','agent_reported')),
  current_run_id        TEXT,
  claimed_at            TEXT,
  run_count             INTEGER NOT NULL DEFAULT 0,
  created_at            TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at            TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE INDEX idx_tasks_status ON tasks(status);
CREATE INDEX idx_tasks_ready ON tasks(status, pinned DESC, priority ASC, created_at ASC);
CREATE INDEX idx_tasks_archived ON tasks(archived_at);
-- 认领查询的热点条件单独建索引，避免全表扫
CREATE INDEX idx_tasks_lease ON tasks(lease_expires_at) WHERE status = 'RUNNING';

-- 任务依赖
CREATE TABLE task_dependencies (
  id          TEXT PRIMARY KEY,
  task_id     TEXT NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
  depends_on  TEXT NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
  type        TEXT NOT NULL DEFAULT 'blocks'
                CHECK (type IN ('blocks','relates')),
  created_at  TEXT NOT NULL DEFAULT (datetime('now')),
  UNIQUE (task_id, depends_on)
);

CREATE INDEX idx_deps_task ON task_dependencies(task_id);
CREATE INDEX idx_deps_depends_on ON task_dependencies(depends_on);

-- 任务模板
CREATE TABLE task_templates (
  id           TEXT PRIMARY KEY,
  name         TEXT NOT NULL,
  description  TEXT,
  preset       TEXT NOT NULL,   -- JSON
  sort_order   INTEGER DEFAULT 0,
  created_at   TEXT NOT NULL DEFAULT (datetime('now'))
);

-- 自定义字段定义
CREATE TABLE custom_field_defs (
  id            TEXT PRIMARY KEY,
  key           TEXT NOT NULL UNIQUE,
  label         TEXT NOT NULL,
  type          TEXT NOT NULL
                  CHECK (type IN ('text','textarea','number','select','multiselect','date','bool','url')),
  required      INTEGER NOT NULL DEFAULT 0,
  default_value TEXT,
  options       TEXT,
  applies_to    TEXT DEFAULT '[]',
  show_on_card  INTEGER NOT NULL DEFAULT 0,   -- 6.9.2：卡片最多显示 2 个，超出时保存拒绝
  sort_order    INTEGER DEFAULT 0,
  enabled       INTEGER NOT NULL DEFAULT 1,
  created_at    TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at    TEXT NOT NULL DEFAULT (datetime('now'))
);

-- 执行 Run
CREATE TABLE task_runs (
  id             TEXT PRIMARY KEY,
  task_id        TEXT NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
  agent_name     TEXT,
  token_id       TEXT REFERENCES api_tokens(id),
  run_number     INTEGER NOT NULL,
  status         TEXT NOT NULL DEFAULT 'RUNNING'
                   CHECK (status IN ('RUNNING','SUCCESS','FAILED','ABANDONED')),
```

# 十二、MCP 工具定义



**传输方式：** HTTP（不使用 stdio；有状态 SSE 还是无状态 Streamable HTTP 待四家客户端实测后定，见 19\.2 第 6 项）  

**端点：** `http://127.0.0.1:7788/mcp`  

**认证：** `Authorization: Bearer <agent-token>`（Agent 专用 Token，与主窗口的 UI 会话 Token 不通用）



|工具|说明|
|---|---|
|`list_ready_tasks`|查询可领取任务（服务端已过滤阻塞，只读，不产生租约）|
|`claim_next_task`|原子认领下一个可执行任务（9\.3）|
|`get_task`|获取任务详情（含审核意见、自定义字段、依赖）|
|`update_progress`|更新进度|
|`append_log`|追加日志|
|`complete_task`|完成，进入待审核（幂等，见下）|
|`fail_task`|失败上报|
|`heartbeat`|续租|
|`get_review_feedback`|获取最近审核意见|


**通用契约：**


- 除 `list_ready_tasks` / `get_task` / `get_review_feedback` 外，所有工具的入参都必须带 `task_id` \+ `run_id` \+ `lease_id` 三元组，校验链与错误语义见 4\.3\.2。
- 租约失效统一返回 `410 LEASE_EXPIRED` / `410 LEASE_REVOKED`，任务被删返回 `409 TASK_GONE`；MCP 层以 `isError: true` \+ `structuredContent.code` 承载同一份错误码（13 章）。
- Agent 收到 `410` 必须丢弃本地结果并停止该 Run 的后续写回，不得重试；重试只对网络错误（连接失败、5xx）有意义。
- Agent 只允许追加 `type = 'log'` 的评论（20\.8），不能写入 `comment` / `status_change`。



## `claim_next_task`



**输入：**

```JSON
{
  "capabilities": ["language:java", "repo:order-service"],
  "task_types": ["缺陷", "子任务"]
}
```

`capabilities` 为**过滤条件**：只领 `task.required_capabilities ⊆ 本 Token 的 capabilities` 的任务（匹配规则见 20\.5）。缺省 `[]` 表示不声明能力，此时只能领 `required_capabilities` 为空的任务。`task_types` 缺省表示不限。



**输出（领到）：**

```JSON
{
  "task": {
    "id": "T-1015",
    "title": "支付回调修复",
    "description": "...",
    "type": "缺陷",
    "priority": 0,
    "tags": ["支付"],
    "custom_fields": {
      "impact_scope": "订单模块",
      "severity": "高"
    },
    "dependencies": {
      "blocks": [],
      "relates": [{"id": "T-1010", "title": "订单模块重构"}]
    },
    "review_feedback": [
      {
        "run_id": "R-2000",
        "conclusion": "REJECT",
        "suggestion": "签名校验需覆盖空值",
        "reason": "边界场景未处理",
        "detail": "请补充 null 和空字符串测试"
      }
    ]
  },
  "lease": {
    "lease_id": "01947c3e-6f2a-7a11-9c31-8d5f2e1b7c40",
    "run_id": "R-2001",
    "expires_at": "2026-09-11T15:00:00Z",
    "ttl_minutes": 30
  }
}
```



**输出（未领到）：** `HTTP 200` \+ `{ "task": null, "reason": "no_ready_task" }`；待执行列非空但全部被能力过滤或阻塞挡住时为 `"all_blocked"`。Agent 据此判断继续等待还是提示用户，不区分两者会退化成"永远轮询空队列"。



## `complete_task`



**输入：**

```JSON
{
  "task_id": "T-1015",
  "run_id": "R-2001",
  "lease_id": "01947c3e-6f2a-7a11-9c31-8d5f2e1b7c40",
  "summary": "修复回调签名验证逻辑，新增 2 个回归测试",
  "artifacts": [
    {"type": "diff", "uri": "artifacts/T-1015/R-2001/01947c3e-8f21-7000-....diff", "size_bytes": 4211, "name": "fix-callback-signature.patch"},
    {"type": "json", "uri": "artifacts/T-1015/R-2001/01947c3e-9a44-7000-....json", "size_bytes": 1802, "name": "回归测试报告"},
    {"type": "link", "uri": "https://github.com/acme/pay/pull/342", "name": "PR #342"}
  ]
}
```

`artifacts[].type` 取值见 6\.10\.1（服务端会按 `mime_type` 重新推导）；`name` 可选，是给界面显示的标签，落 `metadata.name`，缺省时服务端取 `uri` 末段推导（20\.7）。`uri` 的规则分两类：**普通产物**必须是 `POST /api/v1/artifacts` 先落盘后返回的相对路径，不接受绝对路径或 `..`（20\.6）；**`link` 类型**例外，它的 `uri` 就是 `http(s)` 绝对外链、不占磁盘（20\.6），因此也不需要先上传。同一 `run_id` 重复调用返回 200 幂等成功（4\.3\.2）。



## `get_review_feedback`



**输入：** `{"task_id": "T-1015", "limit": 5}`  

**输出：** 最近审核记录数组，元素结构与 `claim_next_task` 中的 `review_feedback` 一致。

# 十三、REST API 定义



## 认证（v1\.5 起：两类凭证，按调用方隔离）



|凭证|适用的接口|传递方式|
|---|---|---|
|UI 会话 Token|用户接口、依赖接口、模板、字段定义、产物接口、数据接口、Token / 设置接口|`Authorization: Bearer <ATB_UI_TOKEN>`|
|Agent Token|任务接口中的 `ready`、`claim`、`progress`、`logs`、`complete`、`fail`、`heartbeat`、`review-feedback`|`Authorization: Bearer <agent-token>`|
|任一即可|`GET /api/v1/tasks/{id}`|两种 Token 均可读|



**跨组拒绝：** Agent Token 不能调用任何用户接口（含审核、设置、Token 生成、备份恢复）；UI Token 不能调用 `claim` / `complete` / `fail` / `heartbeat`。这是 15 章权限矩阵的落地位置，v1\.4 只有矩阵没有约束点。



**资源型端点例外（新架构的必现问题）**：`/artifacts/{id}/raw` 与 `/thumbnail` 由 `<img>`、`iframe`、pdf\.js 直接加载，**无法携带自定义请求头**。处理方式：前端先调用 `GET /api/v1/artifacts/{id}` 换取 **60 秒有效的一次性签名 URL**，再用该 URL 加载资源；不把 UI Token 放进查询参数（会进访问日志）。

### 详情抽屉与列表页的读取模型



`GET /api/v1/tasks/{id}` **只返回任务本体**（字段 \+ `custom_fields` 全量 \+ `required_capabilities` \+ 前置/后续摘要），不内嵌 Run、审核、评论、审计——一次全捞会让抽屉打开时间随执行次数线性变长，而 `comments` 单 Run 上限 5000 行（20\.8）。各界面按下表各自取数：



|界面|接口|载荷要点|
|---|---|---|
|概览（原型 4\.4）|`GET /api/v1/tasks/{id}`|同上；`artifacts` 与 `runs` 不在此响应内|
|执行（4\.5）|`GET /api/v1/tasks/{id}/runs?include=artifacts`|`runs[]` 按 `started_at DESC`；每条含 `artifacts[]`（该 Run 全量，不分页）、`review`（该 Run 的结论与三字段，可为 `null`）、`log_count`|
|执行 · 日志块|`GET /api/v1/runs/{id}/logs?page=&page_size=200`|`comments` 中 `type='log'` 的行，时间正序；界面「加载更早」对应 `page` 递增|
|审核（4\.6）|`GET /api/v1/tasks/{id}/reviews`|三字段恒非空（4\.3）；列名按 20\.2：`conclusion`、`return_to`、`priority_adj`、`created_at`|
|依赖（4\.7）|`GET /api/v1/tasks/{id}/dependencies`|见下方「依赖接口」|
|评论（4\.8）|`GET /api/v1/tasks/{id}/comments?type=comment,status_change&page=`|**不含** `log`，Agent 日志只出现在执行标签|
|审计（4\.10、7\.7）|`GET /api/v1/audit?target_type=&target_id=&page=`|`page_size` 固定 50，时间倒序，无筛选（17\.2）；抽屉传 `target_id`，设置页不传|
|列表页（3\.8）|`GET /api/v1/tasks`|参数见上一张表|
|筛选器的标签候选|`GET /api/v1/tags`|`{tags: []}`，`SELECT DISTINCT` 实时聚合、不落表（20\.3）|



- 抽屉打开只请求「概览」，切到某 Tab 才请求该 Tab 的数据；前端按 `['task', id, tab]` 缓存，来回切 Tab 不重复请求。

- **WS 事件只当失效信号**：收到与当前任务相关的事件即 `invalidate` 对应 Tab，不做本地增量修改。抽屉是单任务视图，重取一次比维护"卡片移动 \+ Run 状态 \+ 日志追加"的增量一致便宜，也避开 20\.7 里看板不做分页的那类边界歧义。

- 三个只增不减的读接口（`logs`、`comments`、`audit`）不提供写入侧的对应物：Agent 只能 `POST /tasks/{id}/logs`，人只能在「评论」Tab `POST /tasks/{id}/comments`，审计由服务端在事务内写入（6\.8）。

# 十四、Agent 接入协议



## 接入步骤



1. 用户在设置页生成 Agent Token。

2. Agent 客户端配置 MCP Server URL `http://127.0.0.1:7788/mcp` 和 Token。

3. Agent 客户端自身配置定时任务，到点调用 `claim_next_task`。

4. 执行中定期 `heartbeat`。

5. 完成后 `complete_task`。

6. 下次领取时，通过 `get_task` 读取审核意见与自定义字段。

    

## 依赖处理



**Agent 无需感知依赖。** 平台侧已在 `claim_next_task` 中过滤掉未满足阻塞依赖的任务。Agent 领到的任务一定是可执行的。



## 并行执行



并行执行由 Agent 客户端自行管理。若 Agent 同时执行多个任务，应：



- 对每个任务独立维护 `task_id`、`run_id`、`lease_id`；

- 对每个 Run 分别发送 `heartbeat` 续租；

- 对每个 Run 分别调用 `update_progress`、`append_log`；

- 对每个 Run 分别调用 `complete_task` 或 `fail_task`。

    

## 接入示例（伪代码）



```Python
while True:
    task = mcp.claim_next_task(capabilities=["java"])
    if not task:
        sleep(60)
        continue
    try:
        while working:
            mcp.heartbeat(task.id, task.run_id, task.lease_id)
            mcp.update_progress(task.id, task.run_id, task.lease_id, 50, "处理中")
        result = execute(task)
        mcp.complete_task(
            task.id, task.run_id, task.lease_id,
            summary=result.summary, artifacts=result.artifacts
        )
    except Exception as e:
        mcp.fail_task(task.id, task.run_id, task.lease_id, error=str(e))
```



## 首批接入



|Agent|接入方式|本期|轮询触发|
|---|---|---|---|
|Qoder|MCP HTTP \+ REST|✅|客户端内置定时任务|
|Claude Code|MCP HTTP \+ REST|✅|客户端内置定时任务 / hooks|
|Codex|MCP HTTP \+ REST|✅|客户端内置定时任务|
|Cursor|MCP HTTP \+ REST|✅|**需外部调度或会话内规则**，见下|


平台侧对四者无差别，接入成本均在 Agent 侧配置。差异只集中在「谁在什么时候调用 `claim_next_task`」这一环。


**Cursor 的两点特殊约束：**


- **没有到点自动调 MCP 工具的调度器。** 其余三家的定时任务/自动化可以直接周期调用 `claim_next_task`；Cursor 的 MCP 工具只在一次会话内由模型调用。因此 Cursor 侧的接入方式是二选一：① 用系统级调度（`launchd` / 任务计划程序）周期执行一段脚本走 REST `POST /api/v1/tasks/claim`；② 在 `.cursor/rules/*.mdc` 中写入"每次会话开始先 `list_ready_tasks`，有可领任务则认领"的规则，由用户主动开启会话驱动。方式 ② 不是真正的无人值守，文档与设置页文案不得把它写成"自动执行"。
- **只支持本地会话。** Cursor 的后台/云端 Agent 运行在用户机器之外，访问不到 `127.0.0.1:7788`；平台按 15 章不监听 `0.0.0.0`、不做公网暴露，因此这类 Agent 不在支持范围内，不为其放宽网络绑定。


四家的 MCP 端点、Token、工具契约完全一致；Cursor 的能力差异不引入任何平台侧分支逻辑。

**认证模型（v1\.5 起）**



上表中的「用户」指 **Tauri 主窗口内的操作**。由于 UI 与 Agent 共用 `7788` 一个端口，「localhost 即可信」不再成立，两条凭证必须独立：



|调用方|凭证|来源|生命周期|
|---|---|---|---|
|主窗口（用户）|`ATB_UI_TOKEN`，随机 32 字节|Tauri 主进程启动时生成，经环境变量注入 sidecar|进程级，不落盘，重启即失效|
|Agent 客户端|`Bearer <agent-token>`|设置页生成，库中只存 `token_hash`|长期有效，可吊销|



**三条硬约束（W1 一并实现，后期补成本高）**



1. **Origin 白名单**：`Access-Control-Allow-Origin` 只取 `tauri://localhost` 或 `http://tauri.localhost`；不回显任意 Origin，不接受 `Origin: null`。

2. **写接口一律要求凭证**：`/review`、`/tokens`、`/data/import`、`/settings/backups/{id}/restore` 等无凭证返回 `401`，禁止「本机来源直接放行」。

3. **产物响应**：`/artifacts/{id}/raw` 带 `X-Content-Type-Options: nosniff` 与 `Content-Disposition`；HTML 预览只在 `sandbox="allow-scripts"` 的**独立源** iframe 内渲染，不与 UI 同源（Agent 上传的 HTML 不可执行到 UI 会话 Token 的域）。



**已知并接受残余风险**



- 本机任意进程可连 `7788`；Origin 白名单只约束浏览器，不约束命令行客户端。若同机进程读到 `ATB_UI_TOKEN`，等同取得用户权限——个人单用户桌面场景接受。

- 因此：**只绑定 `127\.0\.0\.1`，任何情况下不监听 `0\.0\.0\.0`、不做端口转发、不做公网访问。**

# 十六、非功能需求



1. **服务常驻**：独立于主窗口和 Agent 运行；关闭主窗口不退出应用。

2. **固定端口**：默认 7788，可配置；仅绑定 `127\.0\.0\.1`。

3. **端口占用**：启动时检测并提示。

4. **桌面应用**：Tauri 原生主窗口 \+ 托盘图标与菜单；单实例运行。

5. **启动**：双击图标即可启动，无需安装 Node 运行时、无需手动打开浏览器。

6. **数据**：SQLite 单文件，便于备份。

7. **实时**：状态变更 1 秒内推送。

8. **并发**：个人场景，支持数个 Agent 并行领取。

9. **离线**：完全本地，无需外网。

10. **可移植**：Windows / macOS 本期交付；Linux 阶段二（17\.2）。

11. **MCP 模式**：仅 HTTP，不含 stdio；具体是 HTTP/SSE 还是 Streamable HTTP 由四家客户端实测后定（19\.2 第 6 项）。

12. **自定义字段**：字段定义可配置；阶段一支持 5 类控件 \+ 必填校验 \+ 卡片展示，`multiselect`/`date`/`url` 三类控件与筛选分组在阶段二（17\.2）。

13. **产物预览**：阶段一 diff、图片、文本／日志、外链（系统浏览器打开）、下载；Markdown、JSON、HTML、PDF 的渲染器在阶段二。

14. **日志保留**：保留天数、级别可配置；单文件 20 MB 为固定轮转阈值（9\.3），设置页只读展示。

15. **数据库备份**：阶段一手动备份与恢复；自动备份开关、频率、保留份数在阶段二。

16. **依赖**：支持阻塞与关联；循环检测；抓取时自动过滤。

17. **依赖图**：DAG 视图，阶段二。

18. **模板**：预填字段。

19. **导入导出**：JSON 本期；CSV 阶段二。

20. **归档**：手动 \+ 自动（N 天可配置）。

21. **置顶**：优先于优先级。

22. **提醒**：托盘角标 \+ 顶栏铃铛计数本期做（6\.7）；macOS / Windows 系统通知中心推送、声音不做。

23. **多语言**：仅中文。

24. **主窗口**：最小尺寸 960×600；记忆上次的尺寸与位置。

25. **UI 资源**：前端静态资源随应用打包，WebView 从本地协议加载，无网络时界面本身仍可用。

# 十八、验收标准



1. 双击桌面应用，主窗口显示看板，托盘图标出现。

2. 浏览器访问 `http://127.0.0.1:7788/` 返回 404，不再提供看板页面；仅 `/api/v1/*`、`/mcp`、`/ws` 三个前缀可达。

3. Agent 未接入时，用户可在主窗口内正常创建、拖拽、配置任务。

4. 关闭主窗口后，服务继续运行，Agent 仍可领取任务；托盘「打开看板」恢复界面且界面状态保持。

5. 生成 Agent Token，Agent 配置 MCP URL 后领取任务。

6. 任务自动进入「执行中」，看板实时更新。

7. Agent 完成后，任务进入「待审核」。

8. 用户审核，必填建议、原因、详情。

9. 通过 → 已完成；驳回 → 按选择回到待执行（默认）或需求池。

10. Agent 下次领取该任务时，能读到审核意见。

11. **认领并发**：待执行队列仅剩 1 个任务时，两个 Agent 同时 `claim_next_task`，只有一个领到；另一方返回 `{task:null}` 且**不产生任何写入**；胜出方的 `lease_id` 全程未被覆盖，`task_runs` 中该任务只有 1 条 `RUNNING`。

12. 同一 Agent 连续调用 `claim_next_task` 两次，应领取到两个不同任务，可并行执行、独立回写、独立审核。

13. 租约超时后任务回到异常/失败；**超时后 Agent 再调 `complete_task` 返回 `410 LEASE_EXPIRED`，任务停在异常列、产物不入库**（4\.3\.2）。

14. 接入新 Agent，平台侧零改动。

15. 重启服务后，端口不变，Agent 无需重新配置。

16. 自定义字段：新建字段定义后，创建任务时可填写；必填未填不允许拖到待执行。

17. 产物预览：diff 可高亮预览；图片可内嵌显示；超限文件提供下载。

18. 日志保留：设置修改后生效；超期日志自动清理。

19. 数据库备份：点「立即备份」生成 `atb-YYYYMMDD-HHmmss.db` 并出现在列表中；从列表恢复后数据与快照一致、`RUNNING` 全部转为 `FAILED`、恢复前自动生成安全备份（9\.3）。**自动备份定时器与保留份数清理属阶段二**（17\.2），本期不验收。

20. **首批客户端接入**：Qoder、Claude Code、Codex 各自配置 MCP HTTP \+ Token 后可正常领取与回写；Cursor 以系统调度脚本走 REST `claim` 亦可完成一次完整的认领→回写（十四章）。

21. **依赖**：A 依赖 B（阻塞），B 未完成时，Agent 调用 `claim_next_task` 不会领到 A；B 完成后，A 可被领取。

22. **多前置**：A 依赖 B、C（均阻塞），B、C 都完成后 A 可领取。

23. **循环检测**：添加形成环的依赖被拒绝并提示。

24. **置顶**：置顶任务优先于优先级排序被领取。

25. **模板**：选择模板创建任务，字段自动填充。

26. **导入导出**：在**空实例**上导出 JSON 后再导入，任务、字段定义、模板、依赖关系完整恢复（`reassign` 策略下 ID 可变但引用不断链）。非空实例的 `overwrite`／`skip` 行为与 `RUNNING → READY` 归一（6\.12\.2）各验一条，按 13 章错误码逐项核对结果页。

27. **批量归档**：归档后不出现在默认看板，可在已归档中恢复。

28. **自动归档**：已完成超 N 天的任务自动归档，N 在设置中配置。

29. **依赖可视化**：被阻塞任务卡片显示阻塞角标，完成后自动消失。

30. **依赖图**：可打开 DAG 视图，节点与连线正确，点击节点打开详情。

31. **单实例**：应用已运行时再次双击图标，不启动第二个实例与第二个 sidecar，而是聚焦已有主窗口。

32. **鉴权**：不带 `ATB_UI_TOKEN` 的用户接口请求返回 401；浏览器中任意网页发起的跨源请求被 CORS 拒绝；不带 Agent Token 的 `/mcp` 与 `/api/v1/tasks/claim` 返回 401。

33. **离线**：断开外网后，主窗口仍可打开并使用全部本地功能（产物中的外链与 PR 链接除外）。

34. **强制停止**：`RUNNING` 任务点停止 → 二次确认 → 任务进异常列、`stop_reason = 'user_stop'`；该 Run 的 Agent 随后回写拿到 `410 LEASE_REVOKED`，任务状态不变。

35. **幂等回写**：`complete_task` 成功后用同一 `run_id` 再调一次，返回 `200` 且任务仍停在待审核，不产生第二条 Run、不重复通知。

36. **孤儿回写**：Agent 回写时任务已被人工移走 → Run 置 `ABANDONED`，产物与日志仍可在详情「执行记录」查看，任务状态不回滚（9\.3）。

37. **归档死锁**：A 是未完成 B 的 `blocks` 前置，归档 A 被拒并提示下游数量；自动归档遇到同样情况跳过并写 `archive_skipped`，B 仍可见且阻塞角标指向 A。

38. **删除级联**：删除带执行记录与产物的任务，`task_runs`／`reviews`／`artifacts`／依赖边一并清除且磁盘目录被删；确认框包含下游解除阻塞的提示。

39. **拖拽矩阵**：按 4\.5 逐格验证，`❌` 目标显示红色描边且不改状态，`🔒` 目标弹表单、取消后卡片回原位。

40. **能力匹配**：任务 `required_capabilities = ["language:java"]`，只声明 `["language:go"]` 的 Token 既领不到也看不见；声明 `["language:java","tool:maven"]` 的能领（子集判定，20\.5）。

41. **通知与托盘角标**：任务进入待审核时铃铛计数与托盘角标同时 \+1；窗口关闭到托盘后角标仍更新；点击铃铛跳到「待审核」筛选视图，对应通知被标已读后计数回落（通知面板本身属阶段二）。

42. **备份与恢复**：手动备份后修改数据，再从备份恢复，数据回到快照时刻且原库先被安全备份；恢复后原 `RUNNING` 任务全部落在异常列，产物区显示「已丢失」（9\.3、20\.6）。

43. **契约校验**：写入 20\.2 之外的枚举值被 `422` 拒绝；读取历史库中的未知值时界面显示「未知（原值）」而不是白屏（20\.11）。

## 20\.4 时间、时区与数值格式


- **库内**：所有 `*_at` 列统一为 SQLite 原生文本 `YYYY-MM-DD HH:MM:SS`，**UTC**，由 `datetime('now')` 产生。这样 SQL 内的字典序比较与 `datetime()` 函数才可直接用，认领/租约过期判断不依赖应用层时钟。
- **接口出参**：服务端在序列化层统一转为 ISO‑8601 带 `Z`（如 `2026-09-11T15:00:00Z`）。前端**只**消费 ISO 串，不做时区猜测。
- **接口入参**：时间字段接受 ISO‑8601（含或不含 `Z`），服务端归一为库内格式；无法解析 → `422`。
- **`due_at`**：存 `YYYY-MM-DD`，无时区，按用户本地日解读；**仅用于展示与排序，不触发任何提醒或状态变化**。
- **展示**：绝对时间用本地时区；距今 24 小时内用相对时间（`2h前`），与原型 3\.3 一致。
- **时长**：`duration_ms` 为整数毫秒；`progress` 为整数百分比，禁止小数。
- **文件大小**：`size_bytes` 整数字节，前端格式化（B/KB/MB，1 位小数）。
- **租约倒计时**：由前端用本地时钟与 `lease_expires_at` 相减得出，**误差以服务端为准**——倒计时归零不代表已回收，回收动作只在服务端定时任务里发生（9\.3）。

## 20\.5 能力匹配规则


```Plain Text
effective = 入参 capabilities 非空 ? 入参 : api_tokens.capabilities
可领取 ⇔ task.required_capabilities ⊆ effective        （子集，不是交集）
       ⇔ task.type ∈ 入参 task_types（入参为空则不限）
       ⇔ 阻塞依赖已满足（5.4）
```


- 语义：任务声明的能力是**最低要求**，Token 能力集合必须完全覆盖它。空 `required_capabilities` 对任何 Token 可见。
- 标识格式 `namespace:value`，命名空间取小写 ASCII；本期约定的命名空间：`language:`、`framework:`、`repo:`、`tool:`。未定义的命名空间不校验取值、按字符串全等匹配。
- `list_ready_tasks` 与 `claim_next_task` 用同一套过滤；不匹配的任务对该 Token **不可见也不提示原因**（避免把任务列表变成探测接口）。
- 被能力过滤掉的 `READY` 任务仍在看板正常显示，并计入 `blocked_count` 之外的普通计数——能力不匹配不是阻塞。
- `claim_next_task` 的 `reason = "all_blocked"` 同时涵盖"依赖未满足"与"能力不匹配"两种情况，不细分（Agent 无需据此采取不同动作）。

## 20\.6 产物存储契约


|项|契约|
|---|---|
|根目录|`~/.agent-board/artifacts/`（Windows：`%APPDATA%\agent-board\artifacts\`），与 6\.10\.2 一致|
|落盘路径|`{task_id}/{run_id}/{artifact_id}.{ext}`，`ext` 由服务端按推导出的 `type` 白名单赋值（`patch/diff→diff`、`png/jpg/jpeg/gif/webp→image`、`log/txt→text`、`md→markdown`、`json→json`、`html→html`、`pdf→pdf`、其余→`bin`）|
|写入顺序|**除 `link` 外**：Agent 先 `POST /api/v1/artifacts` 拿到 `{id, uri}`，再在 `complete_task` 中引用；引用未上传过的 `uri` → `422`。`link` 不走上传接口，其行由 `complete_task` 直接插入|
|路径校验|普通产物的 `uri` 必须是相对路径，拒绝绝对路径、`..`、反斜杠、软链接目标逃逸；解析后必须仍在产物根目录内。**`link` 的 `uri` 走另一条校验**：必须是 `http(s)` 绝对 URL，且长度 ≤ 2048；不解析成文件路径|
|大小|单文件 ≤ `artifact_max_mb`（默认 20），超出 `413 ARTIFACT_TOO_LARGE`；单 Run 累计 ≤ 200 MB，超出后该 Run 的后续上传被拒并写 `warn` 日志|
|`link` 类型|不占磁盘，`uri` 即外链；`size_bytes` 与 `mime_type` 为 `NULL`，`metadata.name` 建议由 Agent 给出（如 `PR #342`），界面显示 `name` 而**不是裸 URL**；点击交系统默认浏览器，WebView 不导航过去（15 章）|
|删除|任务删除时级联删磁盘文件（4\.3\.1 规则 4）；备份恢复后文件缺失 → `404 ARTIFACT_LOST`（13 章）|
|去重|不做内容寻址去重，同内容多次上传存多份（本地磁盘量级可接受）|

## 20\.7 看板接口数据契约


`GET /api/v1/board` 是看板**唯一**数据源，一次请求返回六列：


**查询参数**（全部可选，缺省即 `view=all` 无过滤）：`view`（`all`/`review`/`failed`/`claimable`/`blocked`，取值见 6\.2 第 5 条）、`priority`（多值）、`type`（多值）、`tags`（多值）、`custom_fields[key]`（多值）。**不接受 `status`**——六列本身就是 `status`，要按状态筛请用视图预设或跳列表页。`count` 与 `has_more` 均在应用这些条件**之后**计算。


```JSON
{
  "generated_at": "2026-09-11T14:20:00Z",
  "columns": [
    {
      "status": "READY",
      "count": 137,
      "has_more": true,
      "tasks": [ { "id": "T-1015", "title": "支付回调修复" } ]
    }
  ],
  "unread_notifications": 4
}
```


- `columns` 固定 6 个元素、固定顺序（4\.1）；某列 `tasks` 为空仍返回该列。
- **不分页**：每列按 5\.6 抓取顺序返回前 `board_column_limit`（50）条，`count` 为**当前 `view` 与筛选条件下**该列的匹配总数（无筛选时即该状态的全部未归档任务数），`has_more = count > limit`。超出部分只能经 `GET /api/v1/tasks?status=`（列表页，6\.1 第 8 条）分页取。看板不提供"加载更多"，避免拖拽排序与抓取顺序在分页边界上产生歧义。
- `tasks[]` 元素（卡片 DTO）：`id`、`title`、`type`、`priority`、`tags[]`、`pinned`、`status`、`progress`（可为 `null`）、`progress_msg`、`lease_expires_at`、`agent_name`、`run_count`、`due_at`、`updated_at`、`blocked{count, by[{id,title}]}`、`artifacts[{id,type,name}]`（最多 5 条，按 `created_at DESC`）、`artifact_count`（真实总数，用于「\+N」）、`custom_fields`（仅 `show_on_card` 的字段）。卡片**不为图标另发请求**。
- `blocked.count > 0` 即渲染阻塞角标；`by` 最多 5 条，超出以 `count` 为准。
- 卡片与产物行的 `artifacts[].name` **不是数据库列**（20\.2 的 `artifacts` 无 `name`）：服务端按 `metadata.name` 优先、否则取 `uri` 末段推导后下发，前端不自行解析 URI。`metadata.name` 的来源是 `complete_task` 的 `artifacts[].name`（12 章）。`link` 类型没有文件名，`name` 必须由 Agent 给出，缺失时显示 `uri` 的 host 段。
- 「执行中」列的按 Token 分组计数（4\.4）由前端从 `agent_name` 聚合，后端不额外下发。
- 归档任务**不出现**在 `board`，只出现在带 `archived=true`／`all` 的 `GET /api/v1/tasks`（6\.1 第 8 条、原型 3\.8）。

## 20\.8 评论与日志的写入方


|`author_type`|`type`|谁能写|说明|
|---|---|---|---|
|`user`|`comment`|UI|人在任务详情里追加的讨论|
|`system`|`status_change`|仅服务端|状态流转自动写，`content` 为固定文案（取自 4\.5 文案表）|
|`agent`|`log`|Agent（`append_log`）|Agent **只能**追加执行日志；不能写 `comment`、不能改他人评论、不能删除|
|`agent`|`status_change`|❌|禁止：状态只能由 12 章工具驱动|


- `author_name`：Agent 侧固定取 `api_tokens.name`，不允许 Agent 自报（防伪造）；`user` 本期恒为 `我`（单用户）。
- `task_runs.agent_name` 同理：**认领成功时由服务端写入 `api_tokens.name` 的副本**，`claim` 的入参里没有这个字段，Agent 无法自报。存副本而非只留 `token_id` 是为了在 Token 吊销后仍读得出当时的执行者；用户在设置页改 Token 名称只影响此后的 Run。
- 日志只追加不修改；单 Run 日志上限 5000 行，超出后保留首 1000 行 \+ 最近 4000 行并在中间插一条系统截断行。

## 20\.10 自定义字段值契约


|定义类型（6\.9\.1 ／ `field_defs.type`）|`custom_fields` 中的 JSON 值|校验|
|---|---|---|
|文本 `text` / 多行文本 `textarea`|string，≤ 200 / 5000 字|必填时非空白|
|数字 `number`|JSON number（非字符串）|`min`/`max` 若在 `options` 中声明则校验|
|单选 `select`|string，必须 ∈ `options[]`|必填时不可空|
|多选 `multiselect`|string[]，元素 ∈ `options[]`，去重|必填时长度 ≥ 1|
|日期 `date`|string `YYYY-MM-DD`|不做时区处理|
|布尔 `bool`|bool|—|
|链接 `url`|string，`http(s)` 开头|仅格式校验，不探测可达性|


- 提交未在 `custom_field_defs` 中登记（或已停用）的键 → `422 VALIDATION_FAILED`，`details[]` 指明键名。
- 字段停用后已存值保留并在详情页灰显；删除字段定义则其历史值一并失效（不做数据迁移，UI 需二次确认）。
- 看板/列表筛选的实现约束：值存在 `tasks.custom_fields` JSON 文本里，按 `custom_fields ->> '$.severity' = '高'` 过滤，**无索引**。本期按单用户桌面量级（≤ 1 万任务）接受全表扫；超过则加表达式索引，不改接口契约。

## 20\.11 契约变更与向前兼容


- 迁移只走 Prisma migration 文件，禁止运行时 `ALTER`；SQLite 加 CHECK 需重建表（`CREATE TABLE new → INSERT SELECT → DROP → RENAME`），迁移脚本须在备份之后执行。
- 枚举**只增不删**：已发布过的取值即使不再产生也要保留在 CHECK 里，否则历史行读不出来。
- 语义变化（如 4\.2 把 `DONE` 定为终态）不改枚举值本身，改的是流转校验（`tasks.status` 不变）。
- 本章任何改动，需同步：11 章 CHECK、12/13 章示例、原型对应控件、以及 19 章结论。
