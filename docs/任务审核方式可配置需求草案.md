## 1. 诉求原文与解读

用户反馈式描述：「任务现在全部都需要人工审批，此功能优化每一个任务都可以设置是否需要人工审批，
也可以配置 agent 自动审核方式，比如创建干净子 agent 进行审核」。

拆解为三层能力：
- C1 任务级开关：是否要人工审核（现在恒=要）。
- C2 自动审核：由 Agent（如「干净子 agent」）替代人出审核结论。
- C3 免审核直通：complete 后直接 DONE、不经任何审核（是 C1+C2 的退化组合，需单独定安全性）。

## 3. 方案骨架（已按 §4 拍板定稿）

1. **任务字段 `review_mode`**（迁移 0020 加列）：枚举 `human`（默认）/ `auto` / `none`，
   REST create/PATCH 可写 + 全局默认键 `default_review_mode`（设置页签）。
   **不变量：`review_mode` 不进 `update_task` 可写键**（执行者不得自豁免），RUNNING 期间 UI 也不可改。
2. **reviews 表加列**（同迁移）：`reviewer_type`（`user`/`agent`）+ `reviewer_name`，
   存量行回填 `user`；审计 `review_submit` 的 actorType 随 reviewer_type 走。
   卡片/详情/审核记录必须能看出「这条结论是谁给的」。
3. **自动审核执行链路（Q2=审核者 Token 认领队列）（已作废，随 §14 裁定【1009 移除中】）**：平台**不起任何进程**，复用十四章外部调度形态——
   - 新 MCP 工具 `claim_next_review`：原子领取一个「待自动审核」任务（REVIEW ∧ `review_mode=auto`
     ∧ track=auto ∧ 未被占用），返回只读载荷（任务 + 产物 + 执行日志 + Run 摘要）；
   - 新 MCP 工具 `submit_review`：回三值结论 `APPROVE / REJECT / ESCALATE`，字段对齐现行审核表单；
   - **利益冲突硬门禁**：审核 Token == 该 Run 执行者 Token → 拒（403 语义新错误码 `SELF_REVIEW_FORBIDDEN`）；
     领取查询直接排除同 Token 已完成的 Run。不新增 Token 角色位，靠这道门禁 + 审核留痕约束；
   - 「干净子 agent」= 调用方另起无上下文会话领队列，平台侧口径只到「非执行者 + 只读载荷」。
4. **`review_track`（升级位，Q3 的落点）（已作废——该列与 `auto` 分流随 §14 裁定【1009 移除中】；本条内 `none`→直接 DONE 的直通语义保留）**：任务加一列（并入迁移 0020）区分
   `auto`（等审核器）/ `human`（人工待审）。三处换轨，不引入新状态、七列矩阵不动：
   - 审核器回 `ESCALATE`，或人点卡片「转人工审核」→ track=human + 推 `review_pending`；
   - track=human 后 `claim_next_review` 不再领取（人优先，防抢跑）；
   - `complete_task` 分流：`human`→REVIEW/track=human（现状不变）；`auto`→REVIEW/track=auto；
     `none`→直接 DONE，评论/审计显式记「免审核直通（review_mode=none）」。
   **不设服务端超时定时器**：没人在线就一直等，人随时可一键转人工——避免隐藏计时器造出不可预期流转。
5. **前端**：创建/编辑面板与快速新建加审核方式选择（默认「人工」，none 选项带警示措辞）；
   REVIEW 列卡片标注「待自动审核 / 待人工」两态 + 「转人工审核」按钮；审核记录 Tab 展示 reviewer 列。
6. **通知**：auto 通过不再推 `review_pending`，新增 kind `review_auto_passed`（点开看结论）；
   `submit_review(REJECT)` 走现行驳回通知链（notification-triggers 6.6/6.7 复用）。
7. **词表/文档同步**：`vocabulary.ts` 回写路径 note 补 submit_review；PRD 4.3/6.6 与本草案同步；
   **应用元数据 shortDescription「结果强制人工审核」改为「默认强制人工审核、任务级显式豁免」**
   （tauri.conf.json + 需求.md 文末核心定位总结 + PRD 定位段三处一致）。

## 4. 分叉拍板（2026-09-28，用户四题全按推荐选定）

- **Q1 定位条款**：**默认人工 + 任务级 opt-in**——默认仍人工审核，选 auto/none 才算显式豁免且全链留痕；
  措辞三处同步改「默认强制人工审核、任务级显式豁免」（见 §3.7）。
- **Q2 审核器形态**：**审核者 Token 认领队列**——新 MCP 工具 `claim_next_review` / `submit_review`，
  平台不起进程，复用十四章外部调度先例；「干净子 agent」= 调用方另起无上下文会话（实现细节见 §3.3）。
- **Q3 兜底**：**不确定→升级人工**——`ESCALATE` 三值 + 卡片「转人工审核」按钮双入口；
  **不设超时定时器**（等待无期限、人可随时接管，行为可预期优先于自动兜底）。
- **Q4 安全底线**：**自由选 + 执行者不可自豁免**——任何建单面可选三值；硬线只有两条：
  `review_mode` 不进 `update_task` 可写键 + 自审门禁 `SELF_REVIEW_FORBIDDEN`。不加副作用类型黑名单（用户裁定）。
- **Q5 全局默认的管辖范围**（实现期补问，2026-09-28，用户按推荐选定）：**「继承，全局设置只管一处口径」**——
  `default_review_mode` 是三条建单路（REST 建单、Agent 直建、拆解确认页建子任务）共用的**唯一**缺省来源，
  建单面显示「跟随全局默认（人工审核）」而不是写死「人工」，显式选了某一值才覆盖它。
  否决的备选是「每条建单路各自一个默认键」——那会让「审核口径」在一处设置里变成三处，与 §3.1 的优先级链冲突。

## 5. 非目标（本期明确排除）

- 技能市场式远端审核服务、任何出本机的网络调用（与热更新草案是两个需求，不合并）。
- REVIEW/BLOCKED 等状态集合的变更（七列不动）。
- 审核 rubric 的自动生成功能（子 agent 审什么、怎么判，Q2 选到实现形态时再定，本期只定接口形状）。

## 6. 实现与走查收口（2026-09-28）

骨架按 §3 原样落地，七列矩阵未动、平台未起任何进程。以下几处是实现期才定形或改口的地方：

1. **`review_track` 是读面恒返回的列**，不只 REVIEW 期间有值：卡片角标要区分「等待自动审核」与「待你审核」
   两态（含「已转由你审核」），所以 DTO 一直带着它，前端不靠状态猜。
2. **自动审核的通知是两枚 kind，不是一枚**：§3.6 只写了「新增 `review_auto_passed`」，实现里 complete 分流进
   自动轨那一刻也需要一条可见记录（`review_auto_pending`，且**不进**通知中心的「待处理」白名单——它在等审核器，
   不是在等你）。词表扩容与 CHECK 在迁移 0020 一次做完，A2 片没再动枚举。
3. **换轨 REST 形状定稿**：`POST /api/v1/tasks/:id/review/escalate`（§3.4 只到「卡片有个按钮」这一层）。
   与审核器 `ESCALATE` 同一个落点：只改 `review_track`，不写 `reviews` 行、不改 `review_mode`、推 `review_pending`。
4. **走查查出的死字段（已修）**：需求类型（`type=需求`）不执行、永远不进 REVIEW，但建单弹窗与快速新建默认就
   给了「审核方式」下拉——用户会以为自己在给一条永不进审核的任务选审核方式。两处都在需求分支里隐藏该项，
   并加了源码扫描门禁（`review-mode-field.test.ts`）防回归。
5. **§3.7 的「三处一致」清单按实况改过**：盘点时假设「需求.md 文末核心定位总结」写着「结果强制人工审核」，
   实际那一节没有这句（原文在 PRD 定位段与应用元数据）。改口落点因此是 `tauri.conf.json` shortDescription、
   `package.json` description、README（首行 + 一句话工作流 + 边界原则）与 PRD 定位段，需求.md 只改 §4.5 正文。
6. **SQLite 单连接串行化**：`complete` 分流要读 `default_review_mode`，在写事务里读 settings 会自锁；
   settings 读取一律提到 `$transaction` 之外。这条对后续任何「事务内读设置」的改动都成立。
