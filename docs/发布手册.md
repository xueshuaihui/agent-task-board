# 发布手册（Release SOP）

> 从源码到 GitHub Release 的完整发布流程。**主路径是推 tag 让 CI 发布**（自 v0.0.2 起），
> 本地手工打包降级为附录（§6），只在 CI 不可用或需要临时验产物时用。
> 配套文档：构建细节见 `README.MD`（路径 A/B/C）；签名口径见 `docs/系统操作使用手册.md` §2.4；
> 各批次产物与修订史见当期发版记录（`docs/发版记录 v0.0.3.md` 起一批一份；
> 更早的 M4 构建记在 `docs/发版记录 v0.0.1.md`，不再逐批追加）。
> **截至本文更新时（2026-09-20）本项目从未发过正式版**，现有 tag 只有 `v0.0.1 / v0.0.2 / v0.0.3` 三个 prerelease。

---

## 0. 版本与通道约定

| 通道 | 何时用 | 产物 |
| --- | --- | --- |
| **prerelease（`v0.x.*`，当前全部发布都属于这一档）** | 里程碑间需要对外分发可用包时 | GitHub Release + x64/arm64 两个 .dmg + SHA256SUMS.txt |
| **正式版（`v1.0.0` 起）** | 验收门禁全过后（尚未发生过） | 同上 + 发版记录 + 勾掉 M4/M5 checklist |

- **tag 是发布批次标识**：`.github/workflows/release.yml` 对 `v0.*` 自动加 `--prerelease`，`v1+` 视为正式版。
- **包内版本号唯一来源**：`apps/desktop/src-tauri/tauri.conf.json` 的 `version`（当前 `0.1.0`）。
  打 `v0.0.x` tag **不必**改它。
- tag 一律 annotated：`git tag -a vX.Y.Z -m "说明"`，说明里写清发布口径与已知限制。
- **首个正式版的前置门禁**：A3 真机验收 7 项 + 四家客户端接入自测全过（见 `docs/发版记录 v0.0.1.md` §5 checklist）。
  ⚠️ **口径冲突待你定**：历史文档把这个门禁写作「打正式 `v0.1.0`」，但按上面的 CI 规则
  `v0.1.0` 仍会被自动标成 prerelease——要么正式版改用 `v1.0.0`，要么给 workflow 的 prerelease 判定加例外。
  **prerelease 批次不受该门禁阻塞**，因此当前三个 `v0.0.x` 发布不构成违规。

## 1. 发布（主路径：推 tag）

```bash
# 1) 本地过门禁（CI 会再跑一遍，但别把明显红的推上去）
npm run typecheck && npm run test

# 2) 确认工作区干净、待发布内容都已在 main
git status --short && git log --oneline -5

# 3) 打 tag 并推送 —— 这一步就是「发布」
git tag -a vX.Y.Z -m "vX.Y.Z prerelease：<一句话定位>

- 主要变更点
- 已知限制"
git push origin main
git push origin vX.Y.Z
```

之后无需动手，CI 自动完成：

| Job | runner | 做什么 |
| --- | --- | --- |
| 打包 x64 | `macos-15-intel` | `npm ci` → `npm run prisma` → `bash scripts/package-release.sh`（门禁→构建→sidecar→.app→.dmg→冒烟→SHA256）→ 上传 artifact |
| 打包 arm64 | `macos-15` | 同上，产出原生 Apple Silicon 包 |
| 创建 Release | `ubuntu-latest` | 汇集双架构 dmg → 合并 `SHA256SUMS.txt` → `gh release create`（`v0.*` 自动 prerelease） |

产物名：`Jarvis Workbench_0.1.0_x64.dmg` / `Jarvis Workbench_0.1.0_arm64.dmg`（+ 合并的 `SHA256SUMS.txt`）。

> **为什么是双包而不是 universal 单包**：sidecar 的 node 二进制取自构建机当前 node（Node 官方无
> universal 发行版），Prisma query engine 同样是按机器架构生成的原生库 → 每个 .app 自带匹配架构的
> node 与引擎，Rosetta 不参与 sidecar 运行。

### 1.1 核验 CI 结果

```bash
gh run list --workflow=release.yml --limit 5
gh run watch <run-id> --exit-status
gh release view vX.Y.Z --json name,tagName,isPrerelease,assets,url
```

> 本机 `gh` 未登录时上面的命令会直接报错——**此时不能声称发布已完成**：要么配好凭据核验，
> 要么在发版记录里写明「CI 结果未核验」。（v0.0.3 就属于后者，记录里已如实标注。）

### 1.2 回填当期发版记录

- 本批次的 `docs/发版记录 vX.Y.Z.md`：产物表填 **CI 实跑产出的最终大小与 SHA-256**
  （从 Release 资产或 `SHA256SUMS.txt` 取，不沿用旧值），修订记录加一条；
- `docs/开发计划-*.md` 快照同步；提交并推送（文档改动不必补打 tag，随下一批走）。

## 2. 失败与重跑

| 现象 | 处理 |
| --- | --- |
| 单架构 job 失败 | 修复提交后 `git tag -d vX.Y.Z && git push origin :vX.Y.Z`，重新打 tag 推送（新 tag 指向修复后的提交） |
| Release 已存在、只想补产物 | 重跑 CI 即可：release job 检测到已存在会走 `gh release upload --clobber` |
| 误发 Release | `gh release delete vX.Y.Z --cleanup-tag`（**先确认没人已在用该包**，删了不可恢复） |
| CI 冒烟失败 | **不要**用 `--skip-smoke` 绕过：两个历史缺陷（sidecar 缺依赖启动失败、既有库水位撞表）都是这步抓出来的 |

## 3. 发布前验证：CI 覆盖 vs 只能人工

CI 已覆盖：typecheck / 单测 / sidecar 装配 / .app 构建 / .dmg / 产物冒烟（`ATB_READY` + REST 401）/ SHA-256。

**只有真机能做**（正式 tag 前必做，prerelease 建议做）：

- [ ] 双击 .app 启动 + 托盘图标出现（验收 1）
- [ ] 关窗口后进程常驻（验收 4）；二次启动不重复实例（验收 31）
- [ ] 断网可用（验收 33）；重启后端口不变（验收 15）
- [ ] 通知铃铛与待审核角标联动（验收 41）
- [ ] ad-hoc 签名产物首启不再报「已损坏」，Gatekeeper「无法验证开发者」拦截与解除路径走得通（手册 §2.4）
- [ ] 四家真实客户端接入自测（MCP / REST 认领到回写闭环）

## 4. 凭据

- **CI 用仓库自带 `GITHUB_TOKEN`**（权限仅 `contents: write`），不需要个人 token，也不落任何人的本地凭据。
- 只有走 §6 本地发布才需要 `GH_TOKEN`：Fine-grained token **必须显式授权目标仓库**，
  未授权时 API 一律 **404（不是 403，别被误导）**，Permissions 需 **Contents: Read and write**，
  编辑授权后即刻生效；**用完撤销**（token 一旦出现在对话/终端历史里就该 regenerate）。
- 本机若无 brew，`gh` 用独立二进制：

```bash
mkdir -p ~/.local/bin && cd /tmp
curl -sL -o gh.zip https://github.com/cli/cli/releases/download/v2.62.0/gh_2.62.0_macOS_amd64.zip
unzip -oq gh.zip -d /tmp/gh-extract && cp /tmp/gh-extract/gh_2.62.0_macOS_amd64/bin/gh ~/.local/bin/gh
```

## 5. 已知坑（实录）

- `resources/sidecar/` 不入库：本地打包前必须按 README 路径 C 第 0 步拷入**与目标架构一致**的 node 二进制
  （历史缺陷 #1 根因）。CI 用构建机 node，无此问题。
- 无头会话下 `tauri build` 的 DMG 步骤必失败（osascript）：`scripts/package-release.sh` 已内置 `hdiutil` 兜底。
- 既有开发库与打包 app 共用 `~/.agent-board/`：本地冒烟一律用临时 `ATB_DATA_DIR`（脚本已如此），别拿真实数据目录试。
- 校验 bundle 内修复是否在位时不要用 BSD `grep "a\|b"`（不支持 `\|` 交替，恒 0 误报），
  用 `node -e "fs.readFileSync(...).includes('...')"`。
- GitHub 上传后会把文件名空格替换为点号（`Jarvis.Workbench_…dmg`），属正常行为。
- 产物在发布前可能被重建：**以发布时实跑 `shasum` 为准**回填发版记录，不沿用旧值。
- macOS 自带 bash 3.2 在中文 locale 下会把 `$VAR` 紧跟的中文首字节并入变量名（`set -u` 直接中断）：
  脚本里 `$VAR` 后接中文一律写 `${VAR}`。

## 6. 附录：本地手工打包（CI 不可用时）

```bash
export PATH="$HOME/.cargo/bin:$PATH"
bash scripts/package-release.sh            # 全流程；--help 看 --skip-gates/--skip-dmg/--skip-smoke
# 产物：apps/desktop/src-tauri/target/release/bundle/{macos/Jarvis Workbench.app, dmg/*.dmg}
```

出包后本地冒烟（模拟 .app 内真实启动）：

```bash
APP="apps/desktop/src-tauri/target/release/bundle/macos/Jarvis Workbench.app"
TMPD=$(mktemp -d)
(ATB_DATA_DIR="$TMPD" ATB_PORT=17994 ATB_UI_TOKEN=abc123def456abc123def456abc123de \
  "$APP/Contents/Resources/sidecar/node" "$APP/Contents/Resources/sidecar/main.js" > /tmp/atb-smoke.log 2>&1 &)
for i in $(seq 1 60); do grep -q ATB_READY /tmp/atb-smoke.log 2>/dev/null && break; sleep 0.5; done
grep ATB_READY /tmp/atb-smoke.log          # 期望 version=0.1.0
curl -s --noproxy '*' -o /dev/null -w "tasks: HTTP %{http_code}\n" http://127.0.0.1:17994/api/v1/tasks
pkill -f "Resources/sidecar/main.js"; rm -rf "$TMPD"   # 期望 401，随后清理
```

手工发布：

```bash
export GH_TOKEN=<你的 token>
cd apps/desktop/src-tauri/target/release/bundle && shasum -a 256 dmg/*.dmg > /tmp/SHA256SUMS.txt && cd -
gh release create vX.Y.Z --title "vX.Y.Z prerelease：<一句话定位>" \
  --notes-file /tmp/release-notes.md --prerelease
gh release upload vX.Y.Z "apps/desktop/src-tauri/target/release/bundle/dmg/Jarvis Workbench_0.1.0_<arch>.dmg" \
  /tmp/SHA256SUMS.txt --clobber
```

> 本地只能出**当前机器架构**的包；双架构产物请始终优先走 CI。
